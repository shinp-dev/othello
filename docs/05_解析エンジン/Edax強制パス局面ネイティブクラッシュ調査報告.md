# Edax強制パス局面ネイティブクラッシュ調査報告

## 1. 文書の目的

2026年9月13日にPixel 8aでスタンダード対局中に発生したアプリプロセス終了について、端末ログ、ネイティブシンボル、ソースコード、実機再現試験を対応付けて記録する。

本書では、端末とツールから直接確認した内容を「確認事実」、確認事実から導いた説明を「原因判断」、今後の追加対応を「推奨」として区別する。

## 2. 結論

直接原因は、Edaxのルート探索にあるパス／終局用の仮想手生成処理が、連結リスト終端の `Move.next` を初期化していないことである。

スタンダードAIの候補評価中、候補着手後の相手がパスになる局面へ入ると、未初期化の `next` が後続の `movelist_sort()` に渡る場合がある。その場合、`move_next_best()` が不正なポインタをたどり、書き込み時に `SIGSEGV` でアプリプロセス全体が終了する。

ローカルでは、パス用の仮想手を生成した直後に `move->next = NULL;` を設定した。Pixel 8a上で修正前に同じネイティブスタックのクラッシュを再現し、修正後は強制パス候補を含む200局面を完走した。既存のEdax実機テスト5件も修正後に完走している。

「百獣の王ライオーン」の画像、バナー、対戦パックJSON、思考時間設定、候補選択ウェイトは直接原因ではない。同じ探索経路を使う他のスタンダード対戦相手でも、条件を満たす盤面では発生し得る。

## 3. 利用者が確認した現象

- スタンダードの対局途中でアプリが突然終了した。
- 発生時は新しい対戦相手「百獣の王ライオーン」との対局だった。
- アプリ画面上のエラー表示ではなく、プロセス自体が終了した。

元の対局について、端末内の `files/local-game-records.jsonl` には進行中棋譜が保存されておらず、終了済みの過去棋譜1件だけが存在した。そのため、元の対局手順をそのまま復元することはできなかった。代わりに、同じコード経路と同じクラッシュ位置を使う独立した再現試験を作成した。

## 5. 元のクラッシュで確認した事実

端末のクラッシュ記録は次の内容だった。

| 項目 | 値 |
| --- | --- |
| 発生日時 | 2026-09-13 17:19:14.753 +0900 |
| プロセス稼働時間 | 約300秒 |
| スレッド | `EdaxEngine` |
| signal | `SIGSEGV` |
| code | `SEGV_ACCERR` |
| fault address | `0x000000730b6645b8` |
| ActivityManager exit reason | `APP CRASH(NATIVE)` |
| status | 11 |

これはAndroidによるメモリ不足終了やバックグラウンド制限ではなく、アプリ内のネイティブコードが不正なメモリへ書き込んだクラッシュである。

主要スタックは次の順序だった。

```text
move_next_best
movelist_sort
PVS_root
aspiration_search
iterative_deepening
search_run
edax_android_analyze
NativeEdax.nativeAnalyze
ProductionStandardCandidateProvider.evaluate
```

未stripの `libedax_jni.so` をNDKの `llvm-addr2line` で解決した結果、最上位のクラッシュ位置は次のコードに対応した。

```c
/* third_party/edax/upstream/src/move.c */
move->next = previous_best->next;
```

逆アセンブルでもクラッシュ命令が書き込み命令であることを確認した。不正な書き込み先は、探索対象の連結リストに混入した壊れた `next` ポインタから得られていた。

## 6. 問題のコード経路

### 6.1 通常の合法手生成

`search_get_movelist()` は合法手を連結リストとして生成する。合法手がないときは、先頭の番兵 `movelist->move[0].next` を `NULL` にする。

### 6.2 パス／終局の特殊処理

`PVS_root()` は合法手が空の場合、配列の2要素目をパスまたは終局表示用の仮想手としてリストへ追加する。

修正前の処理は次の状態だった。

```c
if (movelist_is_empty(movelist)) {
    move = movelist->move->next = movelist->move + 1;
    move->flipped = 0;
    /* ... */
}
```

ここでは `movelist->move[1].next` が設定されない。番兵から仮想手へのリンクは作るが、仮想手から先の終端リンクは作っていない。

### 6.3 Androidブリッジで未初期化値が残る条件

スタンダード候補評価の `edax_android_analyze()` は、候補ごとに次のように `Search` をスタック確保する。

```c
Search search;
search_init(&search);
```

`search_init()` は探索に必要な各フィールドを設定するが、`Search` 構造体全体をゼロ初期化せず、パス時に使われる `movelist.move[1].next` も設定しない。したがって、その値はスタック上に残っていた値に依存する。

一方、通常のAI着手選択に使う `edax_android_choose_best_move()` は `calloc()` で `Search` 全体をゼロ初期化している。この差により、今回の未初期化ポインタはスタンダード候補評価で顕在化しやすい。

### 6.4 クラッシュまでの流れ

```text
スタンダードAIが各合法手を候補評価
  -> ある候補着手後、相手の合法手が0（強制パス）
  -> PVS_rootがパス用の仮想手を作る
  -> 仮想手のnextが未初期化のまま残る
  -> movelist_sortがnextを連結リストとしてたどる
  -> move_next_bestが不正アドレスへ書き込む
  -> SIGSEGVでアプリプロセスが終了
```

未初期化メモリの内容は毎回同じとは限らない。このため、同じ種類の盤面でも常に同じタイミングで落ちるとは限らず、対局中に偶発的に見える。

## 7. 実機再現

### 7.1 再現試験の構成

`EdaxLevelOneStressTest` を追加し、次の条件で試験した。

- 初期局面から正規の合法手だけを進め、到達可能な盤面を生成する。
- 現局面には複数の合法手がある。
- JNIへ最初に渡る候補を着手すると、相手の合法手が0になる。
- その子局面は終局ではなく、手番を戻せば続行可能である。
- 本番の第三者評価データは使わず、テスト内で生成したEdax互換の合成評価ファイルを使う。
- スタンダードと同じ `ProductionStandardCandidateProvider.evaluate()` をEdax level 1で実行する。

再現試験はライオーンのJSON、画像、バナーを読み込まない。コンテンツと独立した条件で同じクラッシュを確認できる。

### 7.2 修正前の結果

Pixel 8aで試験プロセスがネイティブクラッシュした。クラッシュ直前までに記録した代表局面は次のとおりである。

```text

```

再現クラッシュは2026-09-13 17:45:50.469に発生した。

| 項目 | 値 |
| --- | --- |


したがって、元の対局と再現試験は同じ欠陥を通ってクラッシュしたと判断する。

## 8. ローカル修正と修正後試験

パス用仮想手の生成直後に、連結リストの終端を明示した。

```diff
 move = movelist->move->next = movelist->move + 1;
+move->next = NULL;
 move->flipped = 0;
```

修正後、同じPixel 8aで次を確認した。

| 試験 | 結果 | 所要時間 |
| --- | --- | --- |
| 強制パス候補を含む到達可能局面 | 200件完走、クラッシュなし | 7分51秒 |
| 既存Edaxネイティブ実機試験 | 5件中5件成功 | 16秒 |

200件完走は、この1行が未初期化ポインタ経路を遮断することを実機で支持する。ただし、あらゆるEdax探索経路に別の欠陥が存在しないことまで保証する結果ではない。

## 9. 原因ではないと判断したもの

### 9.1 ライオーンのコンテンツ

再現試験はライオーンの対戦パックJSON、立ち絵、表情差分、バナーを使用せずに同じネイティブクラッシュを起こした。したがって、画像欠損や配信の時間差は原因ではない。

### 9.2 AIの候補選択ウェイト

`openingWeights`、`midgameWeights`、`endgameWeights` はEdaxが返した候補順位から着手を選ぶ段階で使われる。クラッシュは、その前段で候補を評価している最中に発生した。

### 9.3 Edax level 1の探索負荷

level 1は多くの中盤局面で浅い探索になる。クラッシュ種別もタイムアウトやメモリ不足ではなく、不正ポインタへの書き込みである。思考時間の長さや探索の重さを直接原因とは判断しない。

### 9.4 評価データ破損

再現にはヘッダと所定サイズを持つ合成評価データを使用した。評価値はゼロだが、同じパス経路と同じクラッシュ位置を再現した。特定の利用者評価ファイルの内容に依存する現象ではない。

## 10. 責任範囲の整理

欠陥そのものは、固定している公式Edaxソースの `PVS_root()` にある連結リスト終端の初期化漏れである。一方、Androidブリッジが候補評価ごとに `Search` を未ゼロ初期化のスタック領域へ置くため、未初期化値が実害として現れた。

よって「アプリとは無関係なEdaxだけの問題」とも、「ライオーン固有の問題」とも整理しない。上流Edaxの初期化漏れを、アプリの候補評価方法が到達可能にした組み合わせの問題である。

ネイティブの `SIGSEGV` はKotlinの `try/catch` では復旧できない。クラッシュ前に不正なポインタ経路をなくす必要がある。

## 11. 影響範囲

- スタンダードAIでEdax候補評価を使う全対戦相手が対象になり得る。
- 「候補着手後に相手が強制パスになる」局面が入口である。
- 連結リストの未初期化値に依存するため、必ずクラッシュするとは限らない。
- 発生すると対局単位の失敗ではなく、アプリプロセス全体が終了する。
- 通常のAI着手選択は `calloc()` を使うため今回と同じ未初期化条件になりにくいが、Edax側のリスト終端漏れ自体は共通ソースに存在する。

## 12. テスト上の不足

既存のEdax実機テスト5件は、評価データ／Bookの検証、終盤解析、AI着手選択を確認していたが、「候補評価した子局面で相手がパスになる」経路を含んでいなかった。そのため、従来の試験が成功していても今回の欠陥を検出できなかった。

今回追加した試験は実際の候補評価経路を使い、強制パス条件を満たす到達可能局面を反復する。ネイティブプロセスクラッシュを検知する回帰試験として保持する。

## 13. 今後の推奨

1. 検証済みの `move->next = NULL;` をAndroid向けEdaxパッチへ正式に記録する。
2. `UPSTREAM.md` と `SHA256SUMS` を更新し、vendoredソースとパッチの対応を維持する。
3. 強制パス候補の実機回帰試験を継続する。
4. 防御を重ねる場合は、`edax_android_analyze()` の `Search search;` を構造体全体のゼロ初期化へ変更し、別途修正前後試験を行う。この変更は今回の実機確認済み修正には含めない。
5. 公式Edaxへのissueまたは修正提案は、ローカル／アプリ側の採用判断後に行う。

## 14. この調査ブランチに含めるもの

- `third_party/edax/upstream/src/root.c` の1行修正
- Android向けEdaxパッチ、由来説明、ハッシュ一覧の更新
- 強制パス候補を反復するPixel 8a実機回帰試験
- 本調査報告と資料索引の更新

認証情報、端末から取得した利用者データ、評価データ本体、ビルド成果物は含めない。
