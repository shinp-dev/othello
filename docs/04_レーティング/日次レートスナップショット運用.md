## スケジューラー比較

### Supabase Cron / pg_cron — 推奨

- DB 所有者が`select public.refresh_rating_daily_snapshot();`をDB内で直接実行でき、HTTPや外部ネットワーク hopがない。
- サービスロール（service_role） キーやデータベース URLをCloudflare/GitHubへ追加しない。
- ジョブは`cron.job`、実行履歴は`cron.job_run_details`、DashboardではCronの履歴でDBと同じ運用境界から確認できる。
- 今回は1日1回の短い集計であり、DB内SQL ジョブというSupabase Cronの用途に一致する。
- 追加される運用資源は`pg_cron` extensionと1 ジョブだけ。ただしextension有効化は本番スキーマ変更なので、029適用とは分けて所有者承認後に行う。

SupabaseはCronが内部でpg_cronを使い、SQL/データベース 関数をネットワーク hopなしで実行し、ジョブ/実行をDB内に記録すると説明しています: <https://supabase.com/docs/guides/cron>

### Cloudflare Cron トリガー — 非推奨

- 定期実行ハンドラーとSupabaseへの認証済みネットワーク callが必要になり、障害点とシークレット境界が増える。
- 公開-facing ワーカーへサービスロール（service_role）相当を置くことはarchitecture違反。信頼済み `cloudflare-admin`へ置く場合でも、DB内だけで完結する処理を外部管理者 境界へ広げる理由がない。
- Cron トリガーはUTCで動作し、トリガー変更の反映に時間がかかる場合がある。

Cloudflareの公式仕様: <https://developers.cloudflare.com/workers/configuration/cron-triggers/>

### GitHub Actions スケジュール — 非推奨

- データベース URL等の本番 シークレット、runner、ネットワーク、dependency installが必要になる。
- GitHubは高負荷時に定期実行ワークフローが遅延し、十分な負荷ではdropされる場合があると明記している。
- リポジトリ/ビルド運用には適するが、単一DB 関数の日次実行を既存Research バッチ ワークフローへ混ぜると責務と監視が不明瞭になる。

GitHubの公式仕様: <https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule>

pg_cronが本番planやPostgres バージョンで利用不能、または将来処理が外部API連携を必須にする場合だけ外部スケジューラーを再評価します。現要件ではSupabase Cron/pg_cronが最小で最も明確です。

- ジョブ名: `daily-rating-snapshot`
