# 旧実装計画

> **履歴資料:** この計画は完了済みです。現在の設計・運用は[技術資料インデックス](../README.md)から参照してください。

1. **段階 1 — 境界と契約**
   - Gradle モジュールと依存規則を作成する。
   - architecture / domain 契約、状態 machine、SQL マイグレーション / RLS / RPC、CI検査を実装する。
2. **段階 2 — ゲーム中核（Game Core）**
   - 変更不能な8×8盤面、合法手生成、石の反転、pass、終了結果、決定的hashを実装する。
   - 単体テストとproperty形式のrandom legal 対局 テストを追加する。
3. **段階 3 / 4 — 端末内製品shell**
   - Composeのhome画面と対局画面を追加する。
   - 小さなViewModelを通して端末内 2人対局を接続し、UIに対局 規則を持たせない。
   - ネットワーク設定がなくても利用できるauth、matchmaking、P2P ポートを用意する。
4. **段階 5〜9 — 交換可能な基盤**
   - 文書化したインターフェースの背後へSupabase実装、WebRTC signaling / DataChannel、結果確定、records / レビュー、Research、アカウント削除、JNI Edaxを追加する。
5. **検証**
   - 単体テスト、端末内 SDKが使える場合のAndroid ビルド / lint、依存境界検査を実行する。

## 当時の作業範囲で完了したhardening

- キュー TTL、cancel、定期確認、候補のatomic ロック、random color 割り当てを持つ公式レート matchmaking RPC。
- 参加者限定で冪等な結果 submissionと、ロック済みの明示的なblack / white確定、サーバー側レート更新。
- 追加型`server_status`、正規 着手保存経路、ユーザーごとの50 記録 / 100 レート履歴保持、非公開 プロフィール tombstone、対局開始レートスナップショット。
- Auth bootstrap トリガー、P2Pのremote disc / fingerprint検証、強制pass、型付きanalysis 評価値。公開前の連盟検証と確認材料 アップロードは初回製品から削除した。
- レビュー追従: 1ユーザー 1つの進行中対局 reservation / lease、参加者限定abandon、atomic submit / finalize、終了状態の保持データのクリーンアップ、厳密な結果ペイロード、内部RPCの既定拒否（deny by default）、Researchの識別情報 切り離し、pgTAP coverage。

## 当時のbeta状態

- 端末内 2人対局と、hosted Supabase / WebRTC オンライン playは縦断的に実行可能だった。
- Supabase URL / キーはコミットせず、AndroidクライアントはGit管理外の端末内設定から公開URL / publishable キーを取得した。
- Edax 4.6 JNIを`arm64-v8a` / `x86_64`向けに同梱し、評価データとbookは利用者がimportし、アプリへ同梱しなかった。
- 対局後レビューは、開始／任意／最終／variation局面、全合法手評価値、exact / heuristic / book種別、cancel、古い結果のreject、識別情報-aware memory キャッシュに対応した。
- ユーザー向けbrandは`ちゃんりば`（`ちゃんとリバーシ`）。正式なPlay applicationIdは`com.shinpstudio.chanriva`で、`com.example.othello`は既存Android namespace / Kotlin パッケージとしてだけ残した。
- アカウント削除はアプリ内から要求し、信頼済みワーカーがサービスロール（service_role） authorityを公開せず処理した。非公開データを削除し、共有記録には匿名tombstoneを残した。
- carrier NAT / TURN率、ネットワーク 切り替え、maker固有のバックグラウンド挙動、thermal / battery、arm64 Edaxの持続性能には物理端末が必要だった。
