# ちゃんりば 実機・エミュレーター確認

再現可能なエミュレーター経路は`scripts/run-emulator-e2e.ps1`です。実際のAndroid Emulatorプロセスを2つ使い、本番と同じ形のSupabase / WebRTC経路を通します。偽の通信路を使うテストはこの実行を代替しません。確認結果はGit管理外の`build/e2e/`配下へ出力します。

## 現行debug APKの実機インストール

現行開発版は`versionCode = 4`、`versionName = 0.2.0`です。JDK 17を指定してビルドし、USBデバッグを許可した端末へインストールします。

```powershell
$env:JAVA_HOME = 'C:\Program Files\Android\Android Studio\jbr'
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
.\gradlew.bat :app:assembleDebug
& "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe" install -r app\build\outputs\apk\debug\app-debug.apk
```

署名鍵が異なる既存アプリを入れ替える場合は、アプリデータが消えるため、先に端末上で対象アプリをアンインストールします。Play提出用のrelease AABとdebug APKを同一成果物として扱ってはいけません。

## 必要な準備

1. Docker Desktopを起動し、固定バージョンのSupabase CLI `2.101.0`をインストールします。`supabase start`を実行し、すべてのマイグレーションを適用します。
2. アプリ内の`アカウント作成`ボタン、またはSupabase Auth DashboardからローカルAuthユーザーを2人作ります。例は`player-a@example.test`と`player-b@example.test`です。パスワードをコミットしないでください。
3. Git管理外の`local.properties`でエミュレーター用経路を設定してビルドします。

   ```properties
   supabase.url=http://10.0.2.2:54321
   supabase.anonKey=<local-anon-key>
   ```

   アプリへサービスロール（service_role）キーを絶対に設定しないでください。`localhost`はエミュレーター自身を指し、エミュレーターからホストへ到達するアドレスではありません。
4. 実行を開始します。PowerShell環境変数を使い、認証情報をリポジトリの外に保ちます。

   ```powershell
   $env:OTHELLO_E2E_PLAYER_A_EMAIL='player-a@example.test'
   $env:OTHELLO_E2E_PLAYER_A_PASSWORD='...'
   $env:OTHELLO_E2E_PLAYER_B_EMAIL='player-b@example.test'
   $env:OTHELLO_E2E_PLAYER_B_PASSWORD='...'
   ./gradlew :app:assembleDebug
   ./scripts/run-emulator-e2e.ps1 -StartSupabase -AutoPlay
   ```

   スクリプトは`Pixel_8a`と`Pixel_8a_B`を`emulator-5554` / `emulator-5556`として起動し、APKをインストールし、アプリデータを消去し、A / Bとしてログインします。その後、通常のController / DataChannel経路で自動対局を2回完了し、対局IDが異なることと両クライアントの`CONFIRMED`を必須とします。デバッグ用の時間切れ実行には`-TimeControlMillis 3000`を使います。この検査用設定は1〜60秒を受け入れます。

## 受入れ確認の順序

1. 両エミュレーターでAPIレベル、パッケージのインストール、アプリ起動を確認し、A / Bでログインします。内部IDと通信路の診断はデバッグビルドだけに表示し、リリースUIへ出してはいけません。
2. 両端末で`対局する`をタップします。最初の端末は`WAITING`のままで、2台目が対局を成立させます。最初の端末が自分だけの`match_notifications`行を観測し、次の定期確認を待たずに`claim_active_match_v2`で対局を取得することを確認します。同じリクエストIDによる定期確認／claimは代替経路として残します。
3. 接続情報の診断には、参加者とepochを限定した`match_signals_v2`を通る想定済みのOFFER / ANSWER交換だけが表示されることを確認します。完全なSDP、認証情報、サービスキーをログへ出してはいけません。
4. DataChannelが`OPEN`になり、両クライアントがepoch 0を指定して`ack_match_started_v2`を1回ずつ呼び、`PLAYING`より前に双方のACKが完了してサーバーの`release_status=ACTIVE`を観測することを確認します。対局通知の購読は割り当て取得後に終了しますが、接続情報の購読は再接続用の情報を受けられるよう`WebRtcMatchCoordinator`の生存期間中だけ維持します。
5. BLACKが先に着手することを確認します。`-AutoPlay`は各側の`MatchController`を通じて最初の合法手を選びます。盤面状態をコピーせず、着手にRealtimeを使いません。
6. 双方から`submit_match_result_v2`で提出し、`CONFIRMED`によってGameRecord 1件とレート更新が作られることを確認します。2回目の対戦相手割り当てを行い、以前の相手端末／DataChannel／接続情報リソースが残っていないことを確認します。
7. デバッグ用ドライバー／偽プロトコルのテスト群を使い、重複、コマンドID再利用、不正なply／ハッシュ、不正対局ID、非合法手を試します。盤面が変化せず、アプリが異常終了しないことが必要です。
8. Wi-Fi / Wi-Fi、Wi-Fi / mobile、carrier / carrierで繰り返します。対局中にバックグラウンド / フォアグラウンド、ロック / unlockを切り替えます。プロセス終了（process death）後に実行中P2P セッションが切断済みと報告される場合はありますが、不正な状態で暗黙に再開してはいけません。

## Edaxのemulator受入れ確認

1. 実際に保存したGameRecordとレビューを開きます。evalをimportしていない状態で解析を開始し、`解析用評価データが設定されていません`を確認します。数値評価値を表示してはいけません。
2. `設定 -> 解析`で、端末内生成した合成evalをSAFからimportします。name、import time、SHA-256 識別情報を確認し、copyがアプリ内の非公開ストレージだけに存在することを確認します。ストレージ権限 promptを表示してはいけません。
3. Bookを未設定のまま、初期局面と主棋譜上の任意plyを解析します。ゲーム中核（Game Core）の全合法手に、盤面上で直接値を表示する必要があります。
4. ply間をすばやく移動し、最後に要求した局面だけが表示されることを確認します。variationを開始し、合法手を着手・解析し、save / return後も変更不能な記録が変化していないことを確認します。
5. 小さな終盤で、値に`exact`種別が付くことを確認します。instrumentationでは別に、Edaxとゲーム中核（Game Core）の合法手集合と決定的outputを比較します。
6. 必要に応じて、テストが作成したheaderだけの空Bookをimportし、load / deleteを確認します。third-party evalやBook テストデータを使用・コミットしてはいけません。

## Debug限定の診断

`matchId`、割り当てdisc、ICE / PeerConnection / DataChannel 状態、送受信packet 件数、ply、状態ハッシュ（state hash）、エラー、開始 ACK状態はEmulator E2Eだけを支援します。リリース UIへ内部ユーザーID、対局ID、hash、transport診断を表示しません。完全なSDP、token、パスワード、確認材料 パスをlogへ出してはいけません。

## 物理端末だけで行う追加確認

emulator 実行はAndroid SDK、Supabase、Realtime、ICE、DataChannel、ライフサイクル、matchmaking、結果確定、プロトコル動作を対象にします。carrier固有のNATやplatform挙動には物理端末が必要です。Wi-Fi↔5G 切り替え、mobile↔mobile、CGNAT / symmetric NAT、STUN-only成功率／TURN必要性、maker固有のバックグラウンド制限、thermal / battery挙動、本番Edax native性能を確認します。

## Emulator受入れ確認の対象外となる製品判断

- 永続的なapplicationIdは`com.shinpstudio.chanriva`です。ランチャーアイコンのリソースと`ちゃんりば`ラベルは実装済みです。残る判断はリポジトリ改名、TURN提供者、Google Playでの公開／署名です。
- Privacy ポリシー（`https://chanriva.shinp-studio.com/privacy`）とアプリ外のWeb アカウント削除（`https://chanriva.shinp-studio.com/account-deletion`）はデプロイ済みです。公開前にsigned リリース / Play生成APKで実行時確認を繰り返します。
- 認証情報をリポジトリへ置かずに、crash / ANR monitoringと段階的rollout ポリシーを決めます。
