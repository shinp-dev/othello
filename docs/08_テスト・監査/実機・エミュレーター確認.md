# ちゃんりば 実機・エミュレーター確認

再現可能なemulator経路は`scripts/run-emulator-e2e.ps1`です。実際のAndroid Emulator プロセスを2つ使い、本番と同じ形のSupabase / WebRTC経路を通します。Fake transport テストはこの実行を代替しません。確認材料はGit管理外の`build/e2e/`配下へ出力します。

## 必要な準備

1. Docker Desktopを起動し、固定バージョンのSupabase CLI `2.101.0`をinstallします。`supabase start`を実行し、すべてのマイグレーションを適用します。
2. アプリ内の`アカウント作成` button、またはSupabase Auth dashboardから端末内 Auth ユーザーを2人作ります。例は`player-a@example.test`と`player-b@example.test`です。パスワードをコミットしないでください。
3. Git管理外の`local.properties`でemulator用経路を設定してビルドします。

   ```properties
   supabase.url=http://10.0.2.2:54321
   supabase.anonKey=<local-anon-key>
   ```

   アプリへサービスロール（service_role） キーを絶対に設定しないでください。`localhost`はhost自身を指し、emulatorからhostへ到達するaddressではありません。
4. 実行を開始します。PowerShell環境変数を使い、認証情報をリポジトリの外に保ちます。

   ```powershell
   $env:OTHELLO_E2E_PLAYER_A_EMAIL='player-a@example.test'
   $env:OTHELLO_E2E_PLAYER_A_PASSWORD='...'
   $env:OTHELLO_E2E_PLAYER_B_EMAIL='player-b@example.test'
   $env:OTHELLO_E2E_PLAYER_B_PASSWORD='...'
   ./gradlew :app:assembleDebug
   ./scripts/run-emulator-e2e.ps1 -StartSupabase -AutoPlay
   ```

   scriptは`Pixel_8a`と`Pixel_8a_B`を`emulator-5554` / `emulator-5556`として起動し、APKをinstallし、アプリ データを消去し、A / Bとしてsign inします。その後、通常のcontroller / DataChannel経路でautoplay 対局を2回完了し、対局IDが異なることと両クライアントの`CONFIRMED`を必須とします。debug タイムアウト 実行には`-TimeControlMillis 3000`を使います。このhookは1〜60秒を受け入れます。

## 受入れ確認の順序

1. 両emulatorでAPI レベル、パッケージ install、アプリ起動を確認し、A / Bでsign inします。内部IDとtransport診断はdebug ビルドだけに表示し、リリース UIへ出してはいけません。
2. 両端末で`対局する`をtapします。最初の端末は`WAITING`のままで、2台目が対局を成立させます。最初の端末が自分だけの`match_notifications` 行を観測し、次の定期確認 intervalを待たずに対局を取得することを確認します。定期確認 / 取得は代替経路として残します。
3. signaling診断には、参加者限定の`match_signaling`を通る想定済みoffer / answer交換だけが表示されることを確認します。完全なSDP、認証情報、service キーをlogへ出してはいけません。
4. DataChannelが`OPEN`になり、両クライアントが`ack_match_started`を1回ずつ呼び、`PLAYING`より前に双方が`bothStartAcked=true`を観測することを確認します。サーバーは双方ACKの後だけ`p2p_started_at`を設定します。対局通知の購読は取得後、signaling 購読は双方ACK後に終了します。
5. blackが先に着手することを確認します。`-AutoPlay`は各側の`MatchController`を通じて最初の合法手を選びます。盤面状態をcopyせず、着手にRealtimeを使いません。
6. 双方から提出し、`CONFIRMED`によってGameRecord 1件とレート更新が作られることを確認します。2回目のmatchmakingを行い、以前の相手端末 / channel / signaling リソースがなくなっていることを確認します。
7. debug driver / Fake プロトコル suiteを使い、重複、コマンド ID再利用、不正ply / hash、不正対局ID、非合法手を試します。盤面が変化せず、アプリが異常終了しないことが必要です。
8. Wi-Fi / Wi-Fi、Wi-Fi / mobile、carrier / carrierで繰り返します。対局中にバックグラウンド / フォアグラウンド、ロック / unlockを切り替えます。プロセス終了（process death）後に実行中P2P セッションが切断済みと報告される場合はありますが、不正な状態で暗黙に再開してはいけません。

## Edaxのemulator受入れ確認

1. 実際に保存したGameRecordとレビューを開きます。evalをimportしていない状態で解析を開始し、`解析用評価データが設定されていません`を確認します。数値評価値を表示してはいけません。
2. `設定 -> 解析`で、端末内生成した合成evalをSAFからimportします。name、import time、SHA-256 識別情報を確認し、copyがアプリ内の非公開ストレージだけに存在することを確認します。ストレージ権限 promptを表示してはいけません。
3. Bookを未設定のまま、初期局面と主棋譜上の任意plyを解析します。ゲーム中核（Game Core）の全合法手に、盤面上で直接値を表示する必要があります。
4. ply間をすばやく移動し、最後に要求した局面だけが表示されることを確認します。variationを開始し、合法手を着手・解析し、save / return後も変更不能な記録が変化していないことを確認します。
5. 小さな終盤で、値に`exact`種別が付くことを確認します。instrumentationでは別に、Edaxとゲーム中核（Game Core）の合法手集合と決定的outputを比較します。
6. 必要に応じて、テストが作成したheaderだけの空Bookをimportし、load / deleteを確認します。third-party evalやBook テストデータを使用・コミットしてはいけません。

## Debug限定の診断

`matchId`、割り当てdisc、ICE / PeerConnection / DataChannel 状態、送受信packet 件数、ply、状態ハッシュ（state hash）、エラー、開始 ACK状態はEmulator E2Eだけを支援します。リリース UIへ内部ユーザーID、対局ID、hash、transport診断を表示しません。完全なSDP、token、パスワード、確認材料 パスをlogへ出してはいけません。

## 物理端末だけで行う追加確認

emulator 実行はAndroid SDK、Supabase、Realtime、ICE、DataChannel、ライフサイクル、matchmaking、結果確定、プロトコル動作を対象にします。carrier固有のNATやplatform挙動には物理端末が必要です。Wi-Fi↔5G 切り替え、mobile↔mobile、CGNAT / symmetric NAT、STUN-only成功率／TURN必要性、maker固有のバックグラウンド制限、thermal / battery挙動、本番Edax native性能を確認します。

## Emulator受入れ確認の対象外となる製品判断

- 永続的なapplicationIdは`com.shinpstudio.chanriva`です。launcher icon リソースと`ちゃんりば` labelは実装済みです。残る判断はリポジトリ rename、TURN provider、Google Playでの公開／署名です。
- Privacy ポリシー（`https://chanriva.shinp-studio.com/privacy`）とアプリ外のWeb アカウント削除（`https://chanriva.shinp-studio.com/account-deletion`）はデプロイ済みです。公開前にsigned リリース / Play生成APKで実行時確認を繰り返します。
- 認証情報をリポジトリへ置かずに、crash / ANR monitoringと段階的rollout ポリシーを決めます。
