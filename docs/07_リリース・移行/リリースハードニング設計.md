# ちゃんりば リリースハードニング設計

状態: 実装ブランチ（`release-hardening`）だけが対象です。この作業では、このブランチのマイグレーションやワーカー変更を本番へ導入しません。この文書はプロトコル v2の契約です。

通常接続と再接続の因果関係を先に知る場合は、[通常接続設計](../02_オンライン対局/通常接続設計.md)と[再接続設計](../02_オンライン対局/再接続設計.md)を参照してください。

## バージョン付き契約が必要な理由

クローズドテスト版APKはProtocol 1を使います。バージョンなしの対戦相手割り当て／結果RPCを呼び、`match_signaling`へ直接書き込みます。これらのオブジェクトをその場で置き換えると、インストール済みAPKを壊します。このためProtocol 2は追加型とし、Protocol 2同士だけを対局させます。互換層は一時的なものです。切替えと削除の条件は後述します。共存中も以前の正式性の弱点を残すわけではありません。Protocol 1の結果関数も同じサーバー棋譜再生境界を使い、トリガーが既存の接続情報直接`INSERT`契約に上限を設けます。

変更前の根本原因は次のとおりです。

- ICE `DISCONNECTED`は診断テキストにすぎず、プロセス再起動後に進行中の対局を取得する方法も端末内チェックポイントもありませんでした。開始済み対局の予約が24時間残る可能性がありました。
- 結果の正式性を2つの同値なクライアント文字列に依存していました。レート更新前に合法手として棋譜を再生し、終了盤面、結果、ハッシュを再計算していませんでした。
- 片側の提出は相手プロセスを待ち、期限切れで結果を破棄していました。終了パケットの送信失敗により、敗者自身の提出さえ妨げられる可能性がありました。
- `abandon_match`は進行中または結果待ちの対局を消去できました。
- クリーンアップ関数に、導入済みの呼出し元がありませんでした。
- 接続情報は参加者が件数上限なく`INSERT`でき、クライアントは全行を繰り返し`SELECT`していました。
- DataChannelへの投入を相手アプリでの適用完了とみなし、ACK／再試行／再同期がありませんでした。
- 対戦相手の割り当ては全体で1つのロックを使い、割り当てを返す前に取得通知を消費していました。

## 対局の正式状態機械

`matches.release_status`がProtocol 2の正式状態です。Protocol 1との共存中だけ`NULL`を許容します。データベースの遷移ガードは、ここにない遷移と終了状態からの全遷移を拒否します。

| 状態 | 意味 | 遷移可能な次状態 |
|---|---|---|
| `MATCHED` | 割り当ては存在するが、P2P／接続情報交換を確認していない | `ACTIVE`, `EXPIRED`, `ABANDONED` |
| `ACTIVE` | 両参加者が現在の接続世代（epoch）のDataChannelをACKした | `RECONNECTING`, `RESULT_PENDING`, `CONFIRMED`, `FORFEIT`, `EXPIRED`, `DISPUTED` |
| `RECONNECTING` | 参加者が相手不在を報告し、45秒の猶予中 | `ACTIVE`, `RESULT_PENDING`, `CONFIRMED`, `FORFEIT`, `EXPIRED`, `DISPUTED` |
| `RESULT_PENDING` | 正式情報ではない終了申告（claim）が、期限付きで証拠待ち | `CONFIRMED`, `FORFEIT`, `EXPIRED`, `DISPUTED` |
| `CONFIRMED` | サーバーが検証した正常結果 | 終了 |
| `FORFEIT` | サーバーが認めた投了／時間切れ／切断負け | 終了 |
| `EXPIRED` | 安全なレート対象結果を確立できなかった | 終了 |
| `DISPUTED` | 正式情報ではない証拠が矛盾した | 終了 |
| `ABANDONED` | 開始前の割り当てが利用者操作でキャンセルされた | 終了 |

`server_status`は一時的なProtocol 1互換の投影として残します。Protocol 2の`CONFIRMED` / `FORFEIT`を`CONFIRMED`へ反映するのは、GameRecordとレート行が存在した後だけです。このため既存Research収集トリガーは、引き続き同じ確定事実を起点にします。`EXPIRED` / `ABANDONED`は`ABANDONED`、`DISPUTED`は`DISPUTED`へ反映します。

リースにはサーバー時刻を使います。

- `MATCHED`: 2分。両ユーザーを無期限に予約せず、non-trickle方式のSDP収集と回数を制限した再試行を行える時間です。
- `ACTIVE`: 15分。各プレイヤーの5分時計では思考時間は合計約10分までで、残り5分を接続・開始処理へ割り当てます。これは異常終了時の安全網であり、対局中の定期確認ではありません。
- 再接続／結果の猶予: 45秒。モバイルネットワークの切替えと新しいnon-trickle方式の接続交渉を行える長さを確保しながら、速やかに意味のある結果へ進めます。

### 切断時の動作

- 正常な退出／投了: 退出する呼び出し元が、自分に不利な申告（claim）を提出します。サーバーは相手を信用せずにその事実を認め、冪等に確定できます。
- 一時的なネットワーク喪失／ICE `DISCONNECTED`: クライアントは最初に1.5秒のデバウンスを行い、epochを消費せず既存の候補ペアが`OPEN`へ戻ることを許します。復旧が引き続き必要なら、対局進行と端末内の単調時計を停止し、残った側が`RECONNECTING`へ入ります。`OPEN`の通信路で再交渉を省略する前に、クライアントはサーバー状態を読みます。端末内Controllerがデバウンスを越えた後、その読み取りが同じepochの`ACTIVE`をまだ返す場合、Coordinatorは同期して終了せず`resume_match_v2`を呼びます。再開RPCと処理中の切断報告は同じ対局をロックします。先に到着した側だけが次のepochを1つ作り、もう一方はその`RECONNECTING`へ参加します。サーバーが`RECONNECTING`のepochでは、現在の接続世代（epoch）の接続情報交換と双方のACKを完了します。サーバーがすでに進んだepochの`ACTIVE`なら双方のACK完了を意味し、別のepochを消費せず棋譜同期を行います。
- `FAILED`、プロセス終了（process death）、強制停止（force stop）、電源断: 残ったプロセスは同じ45秒経路を使います。再起動したプロセスは`claim_active_match_v2`で割り当てを取得し、アプリ内の非公開チェックポイントを読み、新しい接続情報交換（signaling negotiation）を始めます。
- 再接続回数上限は対局全体で共有し、プロセス単位の再試行カウンターにはしません。epoch 0は初回接続交渉、epoch 1〜3だけが再接続用です。`ACTIVE`から4回目の再接続リクエストを受けた場合、epoch 3のまま対局をレート対象外の`EXPIRED`として終了します。
- 期限時点で相手が片側だけ不在: 片側の進行不能申告はレート対象外の`EXPIRED`になります。クライアントは相手不在を証明できないため、その申告から勝者を作りません。
- 双方が相手不在を報告: サーバーはネットワーク分断と両側障害を区別できないため、レート、GameRecord、Research入力のない`EXPIRED`にします。
- 15分の有効なリースまで報告なし: レート対象外の`EXPIRED`にします。
- 終了期限後に戻った端末は対局を再開できません。

フォアグラウンドの参加者は期限到達時の状態照合を1回行います。既存のCloudflare無料枠で動く定期実行ワーカーは補助として、同じサービス限定・件数上限付き保守RPCを10分ごとに呼びます。有料サービスや着手ごとのサーバーへの定期確認は追加しません。

## 結果の正式性と1本の結果処理経路

クライアントは対局ID、冪等リクエストID、正規化済み棋譜（canonical transcript）、終了理由、必要な場合の敗者disc、サイズを制限した時計診断値を提出します。クライアントが計算した結果と最終ハッシュはUX／相互確認用としてAndroid内だけに保持し、正式なRPC入力にはしません。

PostgreSQLの棋譜再生検証器は標準初期盤面から始め、各トークン、合法な反転、必要／不要なpass、連続pass／盤面充足による終了、終了後の着手を決定的に検査します。最終盤面、BLACK / WHITEの石数、勝者、ゲーム中核（Game Core）とResearch検証器が使うProtocol 1互換のFNV状態ハッシュ（state hash）を導出します。

正式性の規則は次のとおりです。

- `NORMAL`: 最初の合法な終了棋譜で`RESULT_PENDING`へ入ります。同じnegotiation epochについて、もう一方の参加者が完全に同じ正規化済み棋譜を2件目の申告として提出した場合だけ`CONFIRMED`になります。不一致は`DISPUTED`、2件目がない場合は45秒後に`EXPIRED`です。どちらもレート対象外で、GameRecord／Research入力を作りません。
- `RESIGNATION`、`TIMEOUT`、明示的な切断退出: 呼び出し元が直ちに確立できるのは自分自身の敗北だけです。根拠のない相手の投了／時間切れ申告は期限を設けて待ち、レート対象外で期限切れにします。
- 予期しない切断: 残った側が相手を報告できるのは、上限付き復旧を開始するためだけです。相手が戻らなければ、報告はレート対象外で期限切れになります。レート対象の`FORFEIT`にはできません。
- 形式不正、非合法、省略、終了後、または不一致の証拠は、レート書き込みの前に拒否します。参加者は任意のユーザーや対局を指定できません。

`match_results_v2(match_id primary key)`が唯一の確定事実です。対局／レート 行をロックした1トランザクションの中で、結果確定は次の順に行います。

1. 変更不能な結果を1回だけ挿入します。
2. GameRecord 1件と、件数を制限した両ユーザー参照を挿入します。
3. `(user, match)`ごとに最大1件のレート履歴行を書き、双方のレートを更新します。
4. 互換用`server_status`を最後に`CONFIRMED`へ変更します。
5. 既存の冪等なResearch収集トリガーに、完成した記録／履歴を観測させます。

再試行やRPC応答喪失時は既存結果を返します。レート、GameRecord、Research収集を再実行できません。SHA-256による証拠ダイジェストはルールセット、対局、参加者、正規化済み棋譜（canonical line）、導出結果／ハッシュ、終了の正式性を結び付けます。別対局へのペイロード再利用を防ぎます。

通常着手を意図的にサーバーへ通さないため、共謀する2アカウントが同じ合法なP2P対局を作り、同じ棋譜を提出する残存リスクはあります。完全に防ぐにはサーバーが対局進行を観測する必要があり、P2P／コスト要件と衝突します。1アカウントだけでレート対象の勝者を選ぶことはできません。正常終了には双方の同一証拠が必要であり、非正常終了で即時に認めるのは呼び出し元自身の敗北だけです。同じ相手との反復による不正利用は監視対象として残ります。

サーバー上は合法な完了対局でも片側しか提出できなかった場合に、将来、明示的に正式ではない端末内／アーカイブ記録として保持するかは未解決です。現在の契約はサーバーGameRecordを作りません。将来アーカイブ経路を作る場合も、検証済みGameRecord、レート、Research利用資格から分離する必要があります。

### `canonical_moves`

Protocol 2の結果申告と確定結果は`NOT NULL`です。空文字列は0 plyの非正常終了棋譜として有効で、未知データとは異なります。共有列`game_records.canonical_moves`は、旧行が未知の場合に備えてクローズドテスト共存中は`NULL`を許容したままです。Protocol 2の確定処理は常に検証済みの非`NULL`値を書きます。検証不能な旧行を捏造しません。Protocol 1がなくなった後、`NULL`行を監査し、製品ポリシーに従って隔離／削除し、制約を検証してから、クリーンアップマイグレーションで共有列を`NOT NULL`にします。

## P2P配信プロトコル v2

通常着手は、順序保証と信頼性のあるWebRTC DataChannelだけで送ります。Supabaseへ着手を書きません。

- 着手は対局ID、コマンドID、ply、直前の状態ハッシュ（state hash）、プロトコルバージョンを含みます。
- 送信側は保留中の着手を最大1件と、その着手後に期待するply／hashを保持します。
- 受信側は着手を再生し、圧縮した棋譜を永続チェックポイントへ保存してから、コマンドIDと結果のply／ハッシュを含む`MoveAck`を送ります。
- ACKを失った場合は同じコマンド IDを回数制限付きで再送します。受理済みの重複着手を2回適用せず、同じACKを返します。
- 再試行上限到達またはシーケンス／ハッシュのずれ後、どちらかの端末が`SyncMessage.REQUEST`を送ります。`SNAPSHOT`が含めるのは、最大240文字の正規化済み棋譜（canonical line）とply／ハッシュです。
- スナップショットはゲーム中核（Game Core）で再生します。同一または一方が接頭辞となる履歴は収束させますが、分岐・不正な履歴を推測で適用せず、再接続／期限切れ処理へ進めます。
- ICE `DISCONNECTED`と`FAILED`を区別し、復旧したDataChannelは対局再開前に再同期します。DataChannelのOPEN待ちは最大10秒、同期は最大3秒、SupabaseのリリースRPCはそれぞれ最大10秒です。通常のコルーチンキャンセルはネットワーク障害として表示せず、再送出します。

通常対局で増えるコストは、実着手ごとに小さな相手端末へのACKが1件で、Supabaseリクエストは0件です。

## プロセス復元とUX

`OnlineMatchRecoveryStore`は非公開チェックポイントを1つ保持します。内容は割り当て、圧縮した正規化済み棋譜（canonical line）、状態ハッシュ（state hash）、時計チェックポイント、任意の終了情報の送信箱（finish outbox）です。トークンやシークレットを含まず、終了状態で削除します。2つ目のサーバー上の対局ログではありません。進行中の着手は端末内とP2Pに残し、最終検証済みの棋譜だけが結果処理へ進みます。

`SharedPreferences.commit()`は、永続化完了を確認できるポートとして使います。端末内で受理した着手、受信した着手ACK、取り込んだ同期棋譜、結果送信用の送信箱は、チェックポイントが成功するまでDataChannelまたは結果RPC境界を越えません。失敗は画面に残し、再試行では同じコマンド／リクエストIDを使います。

認証済みアプリの起動時は次の順に処理します。

1. サーバー側のProtocol 2割り当てがあれば取得します。応答喪失後も冪等です。
2. 割り当てを端末内チェックポイントと照合します。
3. Coordinatorから`resume_match_v2`を1回呼び、サーバー上のepochを取り込み、すべてのOFFER／ANSWER処理を1つのmutexで直列化します。
4. 対局を有効にする前にスナップショットを再生・交換します。
5. 未完了の自分に不利な結果または正常終了結果を、同じ意味のペイロードで再送します。
6. サーバーがすでに終了状態なら、その意味を表示してチェックポイントを削除します。

取得に成功して有効な割り当てがなければ、対応する古い端末内チェックポイントを削除します。タイムアウト、オフライン／デコード障害、コルーチンキャンセル、リポジトリ利用不能時はチェックポイントを残します。これらの結果だけでは、正式な割り当てが存在しないと証明できないためです。

UI状態は排他的で、待ち時間と再試行回数には上限があります。接続中、対局中、着手確認待ち、同期中、再接続中／相手待ち、結果送信中、結果待ち、確定、`FORFEIT`、期限切れ／結果なし、異議あり、キャンセル済みです。英語／日本語リソースは同じIDを共有します。結果提出エラーでは再試行操作を表示します。`FINISHING` / `RESULT_PENDING`から離れるとき、開始前のabandon RPCは絶対に呼びません。

## 接続情報交換（Signaling）v2

`match_signals_v2`を読めるのは2参加者だけで、書き込みは`publish_match_signal_v2`経由だけです。

- 送信者、時刻、期限をサーバーが導出します。
- Protocol 2の`MATCHED`または`RECONNECTING`対局だけを受け入れます。
- BLACKは`OFFER`、WHITEは`ANSWER`を発行します。復旧後にBLACKへOFFERを作らせるため、WHITEは起動通知用の`RESUME`を1回発行できます。
- すべての書き込みは呼び出し元の期待する接続交渉世代（negotiation epoch）を含み、遅れて到着した古いepochの書き込みをサーバー側で拒否します。
- サーバーが受け入れるepochは0〜3だけです。ロールごとのスロット上限と合わせ、両参加者が再試行を調整しても1対局の開始ACK行は8件、接続情報行は最大36件に制限します。
- バイト数を制限します。Java／Kotlinの文字数ではありません。
- 重複するペイロードのダイジェストは冪等に扱います。送信者／種別／epochごとに`OFFER` / `ANSWER`は4行、`RESUME`は1行までです。
- TTLは2分で、インデックス付きクリーンアップを行います。
- 終了済み対局では発行できません。

購読側はRealtimeを確立し、最初のスナップショットを1回取得し、参加時の競合に対する状態照合を最大1回行います。500 msごとに全履歴を`SELECT`しません。Realtimeは起動通知の手段であり、件数を制限した行スナップショットが復旧可能な事実です。

Protocol 1の直接挿入権限は共存中だけ残します。トリガーは、進行中で未開始のProtocol 1対局、BLACKの`OFFER`、WHITEの`ANSWER`だけを許可し、送信者ごとに4行、対局ごとに8行へ制限します。既存の保守処理は開始済み／終了済み行を削除します。既存ワーカーはサービス限定の上限付きバッチ`run_legacy_match_maintenance_v1(100)`を呼びます。スケジューラーは追加しません。Protocol 2のテーブルには`authenticated`ロールの直接書き込み権限がありません。

## 対戦相手の割り当て（Matchmaking）v2

`enqueue_or_match_v2(request_id)`は、最初に呼び出し元の既存の未終了割り当てを返します。これによりenqueue応答とclaim応答のどちらを失っても復旧できます。リクエストIDは1回の待機セッションで固定します。対戦相手の割り当ては`FOR UPDATE SKIP LOCKED`を使い、Protocol 2の候補だけを選びます。全ユーザー共通のadvisoryロックはありません。キュー／進行中対局の一意キーが二重対局を防ぐ最後のガードです。

通知は永続的な起動補助通知であり、割り当てを返す前に消費しません。`claim_active_match_v2`は正式な対局から常に割り当てを再構築できます。キャンセルと割り当てが競合した場合は、同じRPCから割り当てを返します。通常はRealtimeを使い、同じenqueue RPCによる2分間のキューリース更新は75秒に1回だけです。

## Supabase リクエスト上限

ここで数えるのはアプリのPostgRESTリクエストです。WebSocket制御フレーム、1つのRPC内のSQL文、P2Pの着手／ACKフレームは除外します。範囲はどちらのプレイヤーが待機するかで変わります。

| 段階 | 変更前 | V2目標 |
|---|---:|---:|
| 対戦相手割り当ての初回 | enqueue 2回 + claim 1回 + 通知スナップショット | enqueue 2回 + 待機側通知スナップショット1回 + claim 1回（計4回） |
| 待機中の代替経路 | 10秒ごとにRPC 2回（12回/分） | 75秒ごとに冪等RPC 1回（1回/分未満） |
| 接続情報交換 | 挿入2回 + 追従用`SELECT` 2〜40回 | 発行RPC 2回 + 初回`SELECT` 2回 + 状態照合（reconciliation）用`SELECT`最大2回 |
| 開始 | 通常4〜5 RPC、障害経路は相手端末ごとに最大約62回 | ACK RPC合計2回 + 通常0〜2回の短い状態読取り。相手が遅い場合、先行クライアントは最大9回読取り |
| 対局進行 | Supabase 0回、着手ごとにP2Pメッセージ1件 | Supabase 0回、着手 + ACK |
| 正常終了結果／対局後 | 約7リクエスト | 提出RPC 2回 + 結果待ち相手の状態照合最大1回。自動プロフィール／レート読取りなし |
| 片側だけの結果待ち | 5分で最大62回の再提出 | 提出1回 + 早期確認1回 + 期限時の状態照合（reconciliation）1回 |

通常経路は割り当ての起動通知行1件と`OFFER` / `ANSWER`行を作り、正式なRealtime変更イベントは3件です。Realtimeのファンアウト／制御フレームは購読状態によって変わり、アプリRPCではありません。結果確定RPCはレート概要を運び、もう一方のクライアントは上限付き照合1回で終了事実を取得します。結果後にプロフィールを先読みしません。

コールド状態から購読し、待ち時間がなければ、実際の通常対局目標は21〜60リクエストではなく約15〜24リクエストです。上側は開始ACKが遅れた場合で、通常の同時開始は下側に近くなります。重要なのはリクエスト数に上限があり、相手不在中に500 ms／5秒間隔で増え続けないことです。

## クリーンアップと保持

`run_match_maintenance_v2(limit)`と`run_legacy_match_maintenance_v1(limit)`はサービスロール（service_role）限定で、`FOR UPDATE SKIP LOCKED`を使う件数制限付きバッチです。

1. 選択したプロトコルの期限切れ業務状態を終了させます。
2. 同じ件数制限付きバッチで、破棄可能な接続情報行と期限切れキュー行を削除します。
3. 既存の終了状態／GameRecord保持は、確立済みの件数制限付き保持ポリシーへ委ねます。

フォアグラウンドの`reconcile_match_v2(match_id)`は、1参加者の対局へ同じサーバー時刻規則を適用します。このため表示中対局はCronを待たずに収束でき、クライアントが残らないプロセス終了（process death）はCronが修復します。

既存ワーカーは両RPCを10分ごとに`p_limit = 100`で呼び、Supabaseリクエストのタイムアウトを10秒にし、返された終了／接続情報／キュー件数を検証してログへ記録し、バッチ上限到達時は警告を出します。アカウント削除と他プロトコルの保守処理を最後まで動かした後、失敗した定期実行処理を失敗扱いにします。本番導入は別の切替え手順です。

## セキュリティ境界

- すべてのクライアント更新RPCは`auth.uid()`を必須とし、呼び出し元をサーバー側で解決し、対局をロックして、参加者、プロトコル、許可された遷移元状態を検証します。
- すべての`SECURITY DEFINER`関数は`search_path = ''`に固定します。内部の棋譜再生／確定／保守用補助関数の権限を`public`、`anon`、`authenticated`から剥奪します。
- RLSはスナップショットを保護し、`authenticated`ロールへProtocol 2の結果／接続情報テーブルの直接書き込み権限を与えません。
- リクエストID、一意キー、変更不能な終了遷移が、再試行／リプレイ攻撃から保護します。
- 接続情報の種別、ロール、バイト数、スロット件数、状態、TTLが接続情報の増幅を制限します。
- 棋譜再生検証器はレート更新前に、悪意ある正規化済み棋譜の構文／意味を検査します。
- クライアントからのabandonは開始前だけです。開始済み、結果提出済み、終了済み対局は消去できません。

## マイグレーションと協調切替え

段階0 — このブランチ:

- マイグレーション `202608250030_release_match_hardening.sql`、v2 Android コード、テスト、ワーカー呼出しを追加します。
- 本番へ適用せず、ワーカーもデプロイしません。

段階1 — DB先行の共存（所有者承認を得た別作業）:

1. Protocol 1の進行中／保留中対局と`NULL`の正規化済み棋譜行をスナップショット／バックアップ・監査します。
2. 追加型マイグレーションを適用します。
3. Protocol 1のRPCシグネチャ／接続情報の直接書込みが引き続き動くことを確認します。
4. Protocol 2の関数、RLS、Realtime publication、保守処理を手動確認します。
5. RPCの存在を確認した後でだけワーカー コードをデプロイします。

段階2 — クライアント展開:

1. Protocol 2のAPKをクローズドテストへリリースします。
2. 2クライアントで正常終了、プロセス停止、再接続、片側結果、応答喪失のケースを確認します。
3. Protocol 1／2の進行中件数、終了処理、重複制約、RPCエラー、リクエスト使用量を監視します。
4. 所有者がProtocol 1によるオンライン対局の終了を承認した場合だけ、最低オンラインプロトコルを引き上げます。

段階3 — 利用終了待ちとクリーンアップマイグレーション:

1. 最大保持期間1回分以上、Protocol 1の進行中／保留中行が0になるまで待ちます。
2. Protocol 1のキュー／結果RPC、`match_signaling`の直接権限／テーブル／シーケンス、互換通知経路を削除します。
3. 着手を捏造せず旧`NULL`／未検証記録を解決し、共有列の`canonical_moves NOT NULL`制約を検証します。
4. `NULL`を許容するProtocol 2の投影を1つの非`NULL`ライフサイクルへ置き換え、旧状態／列を削除して最終スキーマを文書化します。
5. 安定したProtocol 2の名前だけを残します。またはクリーンアップマイグレーションで1回だけ改名します。

## 検証と手動障害注入

自動テストは、ゲーム中核（Game Core）／棋譜再生境界、ACK喪失／重複／再同期、結果の正式性／冪等性、状態遷移、対戦相手割り当ての応答喪失、接続情報のACL／上限、日本語／英語リソースの同等性を対象にします。ブランチの検証コマンドは最終報告に記載します。

ローカルSupabaseだけへマイグレーションを適用した後、2クライアントで次を手動／エミュレーター確認します。

1. A／Bを起動し、Aのプロセスを停止します。Bが相手待ちへ入り、対局が終了することを確認します。
2. Aのネットワークを無効にし、45秒以内に戻します。新しいsignaling＋棋譜同期で再開することを確認します。
3. ネットワークを戻さず繰り返します。残った片側だけの報告と同時ネットワーク分断報告の両方が、レート対象外の`EXPIRED`となり、GameRecord／レート／Research行を絶対に作らないことを確認します。
4. 結果RPCのコミット直後／応答喪失時に片側プロセスを停止します。再試行後もGameRecord 1件とレート履歴2行だけであることを確認します。
5. enqueue／claimの応答を1つ破棄し、同じリクエストIDを再送して同じ割り当てを得ることを確認します。
6. 着手ACKを1つ破棄し、盤面適用が1回だけで同じコマンドが再試行されることを確認します。シーケンスの欠落を注入し、スナップショットへ収束することを確認します。

この手順には、本番Supabase、Cloudflare、Playコンソール、リリース、署名、シークレット、課金の操作を含めません。
