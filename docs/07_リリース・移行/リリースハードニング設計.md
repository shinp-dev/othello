# ちゃんりば リリースハードニング設計

状態: 実装ブランチ（`release-hardening`）だけが対象です。この作業では、このブランチのマイグレーションやワーカー変更を本番へ導入しません。この文書はプロトコル v2の契約です。

通常接続と再接続の因果関係を先に知る場合は、[通常接続設計](../02_オンライン対局/通常接続設計.md)と[再接続設計](../02_オンライン対局/再接続設計.md)を参照してください。

## バージョン付き契約が必要な理由

closed テスト APKはプロトコル v1を使います。バージョンなしのmatchmaking／結果RPCを呼び、`match_signaling`へ直接書き込みます。これらのobjectを同じ場所で置き換えると、install済みAPKを壊します。このためプロトコル v2は追加型とし、プロトコル v2同士だけを対局させます。互換性layerは一時的なものです。切替えと削除の条件は後述します。共存中も以前の正式性の弱点を残すわけではありません。v1 結果 signatureは同じサーバー replay境界を使い、トリガーが既存の直接signaling `INSERT` 契約に上限を設けます。

変更前の根本原因は次のとおりです。

- ICE `DISCONNECTED`は診断テキストにすぎず、プロセス再起動後に進行中の対局を取得する方法も端末内チェックポイントもありませんでした。開始済み対局の予約が24時間残る可能性がありました。
- 結果の正式性を2つの同値なクライアント文字列に依存していました。レート更新前に合法手replay、終了盤面、結果、hashを再計算していませんでした。
- 片側の提出は相手プロセスを待ち、期限切れで結果を破棄していました。終了packetの失敗により、敗者自身の提出さえ妨げられる可能性がありました。
- `abandon_match`は有効なまたは結果 保留中の対局を消去できました。
- クリーンアップ 関数に導入済みの呼出し元がありませんでした。
- signalingは参加者が件数上限なく`INSERT`でき、クライアントは全行を繰り返しSELECTしていました。
- DataChannelへのenqueueを相手アプリでの適用完了とみなし、ACK／再試行／再同期がありませんでした。
- matchmakingは全体で1つのロックを使い、割り当てを返す前に取得通知を消費していました。

## 対局の正式状態machine

`matches.release_status`がv2の正式状態です。v1との共存中だけnullableです。データベースの遷移 guardは、ここにない遷移と終了状態からの全遷移を拒否します。

| 状態 | 意味 | 遷移可能な次状態 |
|---|---|---|
| `MATCHED` | 割り当ては存在するが、P2P / signalingを確認していない | `ACTIVE`, `ABANDONED` |
| `ACTIVE` | 両参加者が現在の接続世代（epoch）のDataChannelをACKした | `RECONNECTING`, `RESULT_PENDING`, `CONFIRMED`, `FORFEIT`, `EXPIRED`, `DISPUTED` |
| `RECONNECTING` | 参加者が相手不在を報告し、45秒の猶予中 | `ACTIVE`, `FORFEIT`, `EXPIRED`, `DISPUTED` |
| `RESULT_PENDING` | 正式情報ではない終了取得が、上限付きの確認材料待ち | `CONFIRMED`, `FORFEIT`, `EXPIRED`, `DISPUTED` |
| `CONFIRMED` | サーバーが検証した正常結果 | 終了 |
| `FORFEIT` | サーバーが認めた投了／時間切れ／切断負け | 終了 |
| `EXPIRED` | 安全なレート対象結果を確立できなかった | 終了 |
| `DISPUTED` | 正式情報ではない確認材料が矛盾した | 終了 |
| `ABANDONED` | 開始前割り当てがcancelまたは期限切れになった | 終了 |

`server_status`は一時的なv1互換projectionとして残します。v2の`CONFIRMED` / `FORFEIT`を`CONFIRMED`へ反映するのは、GameRecordとレート 行が存在した後だけです。このため既存Research 収集 トリガーは、引き続き同じ確定事実を起点にします。`EXPIRED` / `ABANDONED`は`ABANDONED`、`DISPUTED`は`DISPUTED`へ反映します。

leaseにはサーバー時刻を使います。

- `MATCHED`: 2分。両ユーザーを無期限に予約せず、non-trickle SDP gatheringと上限付き再試行を行える時間です。
- `ACTIVE`: 15分。各player 5分時計では思考時間は合計約10分までで、残り5分を接続・開始overheadへ割り当てます。これは異常終了時の安全網であり、gameplay 定期確認ではありません。
- 再接続／結果の猶予: 45秒。mobile ネットワーク 切り替えと新しいnon-trickle negotiationを行える長さを確保しながら、速やかに意味のある結果へ進めます。

### 切断時の動作

- 正常な退出／投了: 退出する呼び出し元が、自分に不利な取得を提出します。サーバーは相手を信用せずにその事実を認め、冪等に確定できます。
- 一時的なネットワーク喪失／ICE `DISCONNECTED`: クライアントは最初に1.5秒debounceし、epochを消費せず既存候補 pairが`OPEN`へ戻ることを許します。復旧が引き続き必要なら、gameplayと端末内のmonotonic 時計を停止し、残った側が`RECONNECTING`へ入ります。`OPEN`の通信路で再交渉を省略する前に、クライアントはサーバー状態を読みます。端末内Controllerがdebounceを越えた後、その読み取りが同じepochの`ACTIVE`をまだ返す場合、Coordinatorは同期して終了せず`resume_match_v2`を呼びます。resume RPCと処理中の切断報告は同じ対局をロックします。先に到着した側だけが次epochを1つ作り、もう一方はその`RECONNECTING`へ参加します。サーバーが`RECONNECTING`のepochでは現在の接続世代（epoch）のsignalingと双方ACKを完了します。サーバーがすでに進んだepochの`ACTIVE`なら双方ACK完了を意味し、別epochを消費せず棋譜同期を行います。
- `FAILED`、プロセス終了（process death）、強制停止（force stop）、電源断: 残ったプロセスは同じ45秒経路を使います。再起動したプロセスは`claim_active_match_v2`で割り当てを取得し、アプリ内の非公開チェックポイントを読み、新しい接続情報交換（signaling negotiation）を始めます。
- 再接続回数上限は対局全体で共有し、プロセス単位の再試行カウンターにはしません。epoch 0は初回negotiation、epoch 1〜3だけが再接続用です。`ACTIVE`から4回目の再接続リクエストを受けた場合、epoch 3のまま対局をレート対象外の`EXPIRED`として終了します。
- 期限時点で相手が片側だけ不在: 片側の進行不能申告はレート対象外の`EXPIRED`になります。クライアントは相手不在を証明できないため、その申告から勝者を作りません。
- 双方が相手不在を報告: サーバーはネットワーク分断と両側障害を区別できないため、レート、GameRecord、Research入力のない`EXPIRED`にします。
- 15分の有効なリースまで報告なし: レート対象外の`EXPIRED`にします。
- 終了deadline後に戻った端末は対局を再開できません。

フォアグラウンドの参加者はdeadline時の状態照合を1回行います。既存の無料Cloudflare 定期実行 ワーカーは補助として、同じservice限定・件数上限付きmaintenance RPCを10分ごとに呼びます。有料serviceや着手ごとのサーバーへの定期確認は追加しません。

## 結果の正式性と1本の結果処理経路

クライアントは対局ID、冪等リクエストID、正規化済み棋譜（canonical transcript）、終了理由、任意の敗者disc、サイズを制限した時計診断値を提出します。クライアントが計算した結果と最終ハッシュはUX／相互確認用としてAndroid内だけに保持し、正式なRPC入力にはしません。

PostgreSQL replay 検証器は標準初期盤面から始め、各token、合法な反転、必要／不要なpass、連続pass／盤面充足による終了、終了後の着手を決定的に検査します。最終盤面、black / white石数、winner、ゲーム中核（Game Core）とResearch 検証器が使うv1 FNV 状態ハッシュ（state hash）を導出します。

正式性の規則は次のとおりです。

- `NORMAL`: 最初の合法な終了棋譜で`RESULT_PENDING`へ入ります。同じnegotiation epochについて、もう一方の参加者が完全に同じ正規化済みlineを2件目として取得した場合だけ`CONFIRMED`になります。不一致は`DISPUTED`、2件目がない場合は45秒後に`EXPIRED`です。どちらもレート対象外で、GameRecord／Research入力を作りません。
- `RESIGNATION`、`TIMEOUT`、明示的な切断退出: 呼び出し元が直ちに確立できるのは自分自身の敗北だけです。根拠のない相手の投了／時間切れ取得は期限を設けて待ち、レート対象外で期限切れにします。
- 予期しない切断: 残った側が相手を報告できるのは、上限付き復旧を開始するためだけです。相手が戻らなければ、報告はレート対象外で期限切れになります。レート対象のforfeitにはできません。
- 形式不正、非合法、省略、終了後、または不一致の確認材料は、レート 書き込みの前に拒否します。参加者は任意のユーザーや対局を指定できません。

`match_results_v2(match_id primary key)`が唯一の確定事実です。対局／レート 行をロックした1トランザクションの中で、結果確定は次の順に行います。

1. 変更不能な結果を1回だけinsertします。
2. GameRecord 1件と、件数を制限した両ユーザー参照をinsertします。
3. `(user, match)`ごとに最大1件のレート履歴行を書き、双方のレートを更新します。
4. 互換用`server_status`を最後に`CONFIRMED`へ変更します。
5. 既存の冪等Research 収集 トリガーに、完成した記録／履歴を観測させます。

再試行やRPC応答喪失時は既存結果を返します。レート、GameRecord、Research 収集を再実行できません。SHA-256 確認材料 ダイジェストはruleset、対局、参加者、正規化済み棋譜（canonical line）、導出結果／hash、終了の正式性を結び付けます。別対局へのペイロード replayを防ぎます。

通常着手を意図的にサーバーへ通さないため、共謀する2 アカウントが同じ合法なP2P 対局を作り、同じlineを提出する残存リスクはあります。完全に防ぐにはサーバーがgameplayを観測する必要があり、P2P／コスト要件と衝突します。1 アカウントだけでレート対象の勝者を選ぶことはできません。正常終了には双方の同一確認材料が必要であり、非正常終了で即時に認めるのは呼び出し元自身の敗北だけです。同じ相手との反復による不正利用は監視対象として残ります。

サーバー上は合法な完了対局でも片側しか提出できなかった場合に、将来、明示的に正式でない端末内／archive 記録として保持するかは未解決です。現在の契約はサーバー GameRecordを作りません。将来archive経路を作る場合も、検証済みGameRecord、レート、Research利用資格から分離する必要があります。

### `canonical_moves`

プロトコル v2の結果 取得と結果は`NOT NULL`です。空テキストは0 plyの非正常終了 lineとして有効で、未知データとは異なります。共有列 `game_records.canonical_moves`は、legacy 行が未知の場合に備えてclosed テスト共存中はnullableのままです。v2確定処理は常に検証済みのnon-null値を書きます。検証不能なlegacy 行を捏造しません。v1がなくなった後、`NULL` 行を監査し、製品ポリシーに従って隔離／削除し、制約を検証してから、クリーンアップ マイグレーションで共有列を`NOT NULL`にします。

## P2P配信プロトコル v2

通常着手は、順序保証と信頼性のあるWebRTC DataChannelだけで送ります。Supabaseへ着手を書きません。

- 着手は対局ID、コマンド ID、ply、previous 状態ハッシュ（state hash）、プロトコル バージョンを含みます。
- 送信側は保留中の着手を最大1件と、その着手後に期待するply／hashを保持します。
- 受信側は着手をreplayし、compact lineを永続チェックポイントしてから、コマンド IDと結果ply／hashを含む`MoveAck`を送ります。
- ACKを失った場合は同じコマンド IDを回数制限付きで再送します。受理済みの重複着手を2回適用せず、同じACKを返します。
- 再試行上限到達またはsequence／hashのずれ後、どちらかの端末が`SyncMessage.REQUEST`を送ります。`SNAPSHOT`が含めるのは、最大240文字の正規化済み棋譜（canonical line）とply／hashです。
- スナップショットはゲーム中核（Game Core）でreplayします。同一／prefixの履歴は収束させますが、分岐・不正な履歴を推測で適用せず、再接続／期限切れ処理へ進めます。
- ICE `DISCONNECTED`と`FAILED`を区別し、復旧したDataChannelは対局再開前に再同期します。DataChannel open待ちは最大10秒、同期は最大3秒、Supabase リリース RPCはそれぞれ最大10秒です。通常のcoroutine キャンセルはネットワーク 障害として表示せず、再throwします。

通常対局で増えるコストは、実着手ごとに小さな相手端末 ACK 1件、Supabase リクエストは0件です。

## プロセス復元とUX

`OnlineMatchRecoveryStore`は非公開チェックポイントを1つ保持します。内容は割り当て、圧縮した正規化済み棋譜（canonical line）、状態ハッシュ（state hash）、時計チェックポイント、任意の終了情報の送信箱（finish outbox）です。tokenやシークレットを含まず、終了状態で削除します。2つ目のサーバー上の対局ログではありません。有効な着手は端末内＋P2Pに残し、最終検証済みlineだけが結果処理へ進みます。

`SharedPreferences.commit()`は、永続化完了を確認できるポートとして使います。端末内で受理した着手、受信した着手ACK、取り込んだ同期棋譜、結果送信用のoutboxは、チェックポイントが成功するまでDataChannelまたは結果RPC境界を越えません。失敗は画面に残し、再試行では同じコマンド／リクエストIDを使います。

認証済みアプリの起動時は次の順に処理します。

1. サーバー側のv2 割り当てがあれば取得します。応答喪失後も冪等です。
2. 割り当てを端末内チェックポイントと照合します。
3. Coordinatorから`resume_match_v2`を1回呼び、サーバー上のepochを取り込むし、すべてのoffer／answer作業を1つのmutexで直列化します。
4. 対局を有効にする前にスナップショットをreplay・交換します。
5. 未完了の自分に不利な結果／正常終了 結果を、同じペイロードの意味で再送します。
6. サーバーがすでに終了状態なら、その意味を表示してチェックポイントを削除します。

取得に成功して有効な割り当てがなければ、対応する古い端末内チェックポイントを削除します。タイムアウト、オフライン／デコード 障害、coroutine キャンセル、リポジトリ利用不能時はチェックポイントを残します。これらの結果だけでは、正式な割り当てが存在しないと証明できないためです。

UI 状態は排他的で上限があります。接続中、対局中、着手確認待ち、同期中、再接続中／相手待ち、結果送信中、結果待ち、確定、forfeit、期限切れ／結果なし、異議あり、cancel済みです。英語／日本語リソースは同じIDを共有します。結果提出エラーでは再試行操作を表示します。`FINISHING` / `RESULT_PENDING`から離れるとき、開始前abandon RPCは絶対に呼びません。

## Signaling v2

`match_signals_v2`を読めるのは2参加者だけで、書き込みは`publish_match_signal_v2`経由だけです。

- sender、時刻、期限をサーバーが導出します。
- プロトコル v2の`MATCHED`または`RECONNECTING` 対局だけを受け入れます。
- BLACKは`OFFER`、WHITEは`ANSWER`をpublishします。復旧後、BLACKにofferを作らせるため、WHITEはwake-up用`RESUME`を1回publishできます。
- すべての書き込みは呼び出し元の期待する接続交渉世代（negotiation epoch）を含み、遅れて到着した古いepochの書き込みをサーバー側で拒否します。
- サーバーが受け入れるepochは0〜3だけです。ロールごとのスロット上限と合わせ、両参加者が再試行を調整しても1対局の開始 ACK 行は8件、signal 行は最大36件に制限します。
- byte sizeを制限します。Java／Kotlinの文字数ではありません。
- 重複ペイロード ダイジェストは冪等です。sender／type／epochごとに`OFFER` / `ANSWER`は4 行、`RESUME`は1行までです。
- TTLは2分で、インデックス付きクリーンアップを行います。
- 終了済み対局はpublishできません。

subscriberはRealtimeを確立し、最初のスナップショットを1回取得し、join 競合に対する状態照合を最大1回行います。500 msごとに全履歴をSELECTしません。Realtimeはwake-up手段であり、制限された行 スナップショットが復旧可能な事実です。

v1の直接insert権限は共存中だけ残します。トリガーは、実行中で未開始のv1対局、BLACK `OFFER`、WHITE `ANSWER`だけを許可し、senderごとに4 行、対局ごとに8 行へ制限します。既存maintenanceは開始済み／終了済み行を削除します。既存ワーカーはservice限定の上限付きバッチ `run_legacy_match_maintenance_v1(100)`を呼びます。スケジューラーは追加しません。v2 テーブルにはauthenticated ロールの直接書き込み権限がありません。

## Matchmaking v2

`enqueue_or_match_v2(request_id)`は、最初に呼び出し元の既存非終了割り当てを返します。これによりenqueue 応答と取得 応答のどちらを失っても復旧できます。リクエストIDは1 waiting セッションで固定します。matchingは`FOR UPDATE SKIP LOCKED`を使い、プロトコル v2 候補だけを選びます。全ユーザー共通のadvisory ロックはありません。キュー／有効なの一意 キーが二重対局を防ぐ最後のguardです。

通知は永続的なwake-up 補助通知であり、割り当てを返す前に消費しません。`claim_active_match_v2`は正式な対局から常に割り当てを再構築できます。cancelと割り当てが競合した場合は、同じRPCから割り当てを返します。通常はRealtimeを使い、同じenqueue RPCによる2分キュー leaseの更新は75秒に1回だけです。

## Supabase リクエスト上限

ここで数えるのはアプリのPostgREST リクエストです。WebSocket control frame、1 RPC内のSQL statement、P2P 着手／ACK frameは除外します。範囲はどちらのplayerが待機するかで変わります。

| 段階 | 変更前 | V2目標 |
|---|---:|---:|
| matchmaking初回 | 2 enqueue + 1 取得 + 通知 スナップショット | 2 enqueue + 1 待機側 通知 スナップショット + 1 取得（4） |
| waiting 代替経路 | 2 RPC / 10秒（12/min） | 1 idempotent RPC / 75秒（1/min未満） |
| signaling | 2 insert + 2〜40 catch-up SELECT | 2 publish RPC + 2 initial SELECT + 最大2 状態照合（reconciliation） SELECT |
| 開始 | 通常4〜5 RPC、障害 パスは最大約62/相手端末 | ACK RPC合計2 + 通常0〜2 short 状態 読み取り。相手が遅い場合、先行クライアントは9 読み取りまで |
| gameplay | Supabase 0、着手ごとにP2P メッセージ 1 | Supabase 0、着手 + ACK |
| 正常終了 結果／対局後 | 約7 リクエスト | submit RPC 2 + 保留中 相手端末の状態照合最大1。自動プロフィール／レート 読み取りなし |
| one-sided 保留中 | 5分で最大62 resubmit | submit 1 + early check 1 + deadline 状態照合（reconciliation） 1 |

通常経路は割り当て wake 行 1件と`OFFER` / `ANSWER` 行を作り、正式なRealtime change eventは3件です。Realtime fan-out／control frameは購読状態によって変わり、アプリ RPCではありません。結果確定RPCはレート 概要を運び、もう一方のクライアントは上限付き照合1回で終了事実を取得します。結果後にプロフィールを先読みしません。

cold 購読で待ち時間がなければ、実際の通常対局目標は21〜60 リクエストではなく約15〜24 リクエストです。上側は開始 ACKが遅れた場合で、通常の同時開始は下側に近くなります。重要なのはリクエスト数に上限があり、相手不在中に500 ms／5秒間隔で増え続けないことです。

## クリーンアップと保持

`run_match_maintenance_v2(limit)`と`run_legacy_match_maintenance_v1(limit)`はサービスロール（service_role）限定で、`FOR UPDATE SKIP LOCKED`を使う件数制限付きバッチです。

1. 選択したプロトコルの期限切れbusiness 状態を終了させます。
2. 同じ件数制限付きバッチで、破棄可能なsignaling 行と期限切れキュー 行を削除します。
3. 既存の終了状態／GameRecord保持は、確立済みの件数制限付き保持 ポリシーへ委ねます。

フォアグラウンドの`reconcile_match_v2(match_id)`は、1参加者の対局へ同じサーバー時刻規則を適用します。このため表示中対局はCronを待たずに収束でき、クライアントが残らないプロセス終了（process death）はCronが修復します。

既存ワーカーは両RPCを10分ごとに`p_limit = 100`で呼び、Supabase リクエストのタイムアウトを10秒にし、返された終了／signal／キュー件数を検証してlogへ記録し、バッチ上限到達時はwarningを出します。アカウント削除と他プロトコルのmaintenanceを最後まで動かした後、失敗した定期実行 workを失敗扱いにします。本番導入は別のcutover stepです。

## セキュリティ境界

- すべてのクライアント更新RPCは`auth.uid()`を必須とし、呼び出し元をサーバー側で解決し、対局をロックして、参加者、プロトコル、許可された遷移元状態を検証します。
- すべての`SECURITY DEFINER` 関数は`search_path = ''`に固定します。内部replay／finalize／maintenance helperの権限を`public`、`anon`、`authenticated`から剥奪します。
- RLSはスナップショットを保護し、authenticated ロールへv2 結果／signal テーブルの直接書き込み権限を与えません。
- リクエストID、一意 キー、変更不能な終了遷移が、再試行／replayを保護します。
- signal type、ロール、byte size、スロット 件数、状態、TTLがsignaling増幅を制限します。
- replay 検証器はレート更新前に、悪意ある正規 syntax／semanticsを検査します。
- クライアント abandonは開始前だけです。開始済み、結果提出済み、終了済み対局は消去できません。

## マイグレーションと協調cutover

Stage 0 — このブランチ:

- マイグレーション `202608250030_release_match_hardening.sql`、v2 Android コード、テスト、ワーカー呼出しを追加します。
- 本番へ適用せず、ワーカーもデプロイしません。

Stage 1 — DB-first共存（所有者承認を得た別作業）:

1. v1の有効な／保留中 対局とnull 正規 行をスナップショット／backup・監査します。
2. 追加型マイグレーションを適用します。
3. v1 RPC signature／直接signalingが引き続き動くことを確認します。
4. v2 関数、RLS、Realtime publication、maintenanceを手動確認します。
5. RPCの存在を確認した後でだけワーカー コードをデプロイします。

Stage 2 — クライアント rollout:

1. v2 APKをclosed テストへリリースします。
2. 2 クライアントで正常終了、プロセス kill、再接続、片側結果、応答喪失のケースを確認します。
3. v1／v2 有効な件数、終了処理、重複制約、RPC エラー、リクエスト使用量を監視します。
4. 所有者がv1 オンライン playの終了を承認した場合だけ、最低オンライン プロトコルを引き上げます。

Stage 3 — drainとクリーンアップ マイグレーション:

1. 最大保持 window 1回分以上、v1 有効な／保留中 行が0になるまで待ちます。
2. v1 キュー／結果RPC、`match_signaling`の直接grant／テーブル／sequence、互換通知経路を削除します。
3. 着手を捏造せずlegacy null／未検証記録を解決し、共有`canonical_moves NOT NULL`を検証します。
4. nullableなv2 projectionを1つのnon-null ライフサイクルへ置き換え、legacy 状態／列を削除して最終スキーマを文書化します。
5. 安定したv2 nameだけを残します。またはクリーンアップ マイグレーションで1回だけrenameします。

## 検証と手動fault injection

自動テストは、ゲーム中核（Game Core）／replay境界、ACK 喪失／重複／再同期、結果の正式性／冪等性、状態 遷移、matchmaking 応答喪失、signaling ACL／上限、日本語／英語リソース 同等性を対象にします。ブランチの検証コマンドは最終報告に記載します。

端末内 Supabaseだけへマイグレーションを適用した後、2 クライアントで次を手動／emulator確認します。

1. A／Bを起動し、Aのプロセスをkillします。Bが相手待ちへ入り、対局が終了することを確認します。
2. Aのネットワークを無効にし、45秒以内に戻します。新しいsignaling＋棋譜同期で再開することを確認します。
3. ネットワークを戻さず繰り返します。残った片側だけの報告と同時partition報告の両方が、レート対象外の`EXPIRED`となり、GameRecord／レート／Research 行を絶対に作らないことを確認します。
4. 結果RPC コミット直後／応答喪失時に片側プロセスをkillします。再試行後もGameRecord 1件とレート履歴2行だけであることを確認します。
5. enqueue／取得 応答を1つdropし、同じリクエストIDを再送して同じ割り当てを得ることを確認します。
6. 着手ACKを1つdropし、盤面適用が1回だけで同じコマンドが再試行されることを確認します。sequence gapを注入し、スナップショットへ収束することを確認します。

この手順には、本番Supabase、Cloudflare、Play コンソール、リリース、署名、シークレット、billingの操作を含めません。
