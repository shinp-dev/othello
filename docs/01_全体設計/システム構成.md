# ちゃんりば システム構成

実行基盤、Cron / スケジュール、シークレット境界、運用主体、障害確認先などの運用責務は[運用マップ](運用マップ.md)を正本として参照します。Supabase / Cloudflare / GitHub Actions間で処理を追加・移動する場合は、設計変更前にこの台帳を確認し、変更後に必ず更新します。

## 対象範囲

このリポジトリは、Androidを中心とするリバーシ製品「ちゃんりば」を実装しています。認証済みのローカル対局、Supabaseを使う対戦相手の割り当て（matchmaking）と結果確定、WebRTC DataChannel対局、変更不能な記録、アカウント削除処理、対局後のEdaxレビューを、明示したdomain境界の内側へ実装しています。

ローカル対局を含むAndroid アプリ全体で、利用者のログインを必須とします。認証はアプリへ入るための要件ですが、入った後のローカルゲーム規則と端末内記録はSupabaseのデータ アクセスから独立しています。

## 依存方向

```text
app -> feature/* -> core/*
app -> analysis:edax -> analysis:api -> core:game
feature:review -> analysis:api
feature:match -X-> analysis:edax
transport:webrtc -> core:network
data:supabase -> feature ports / core contracts
feature:match -X-> feature:profile
```

`core:game`はAndroidへ依存しません。`feature:match`が利用するのは`GameState`とtransport ポートだけです。対局 ソースが`analysis`を参照すると、ビルド時の境界検査が失敗します。Supabase SDKの型は`:data:supabase`の内部だけで使い、`SupabaseModule`が公開するのはアプリ所有のポートだけです。WebRTC SDKの型は`:transport:webrtc`の内部だけで使い、呼出し側へは`MatchTransport`、ペイロード、基本的な診断値を返します。

## アプリ所有のHTTP境界と起動判定口

Android／Web クライアントに向けたアプリ所有の外部公開HTTP APIは、原則として公開用Cloudflare ワーカーへ置きます。このワーカーはアプリ設定、Web アカウント API、その他のクライアント-facing HTTP endpointを担当します。同種のAPIを1つの境界へ集めることで、実装場所、運用、調査、セキュリティ境界、責任を明確にします。

SupabaseはAuth、PostgreSQL、RLS、RPC、Realtimeを担当します。明確な設計理由がない限り、アプリのHTTP APIをSupabase Edge Functionsなど複数のSupabaseの公開面へ分散させません。このためAndroidの最低対応バージョンは、秘密ではないワーカー変数を参照する公開Cloudflareエンドポイント `GET /api/app-config`から取得し、Supabaseへ問い合わせません。

`cloudflare-admin`は、別の信頼済み管理境界です。サービスロール（service_role） アクセス、`ADMIN_TOKEN`、信頼済みmaintenance／管理者処理を担当します。一般利用者向けAPIをここへ置かず、公開用ワーカーを信頼済み管理ワーカーとして扱いません。

Android プロセスの起動では、次の判定口を順番に通ります。

```text
VersionGate
  -> Supported: AuthGate
       -> Authenticated: AuthenticatedApp
```

`VersionGate`が判断するのは、`BuildConfig.VERSION_CODE`が対応範囲かどうかだけです。設定を確認中、取得不能、不正値の場合はアプリへ進ませません。`OnlineSessionViewModel`、Supabase component、Auth/セッション ライフサイクルは、`VersionGate`が`Supported`になった後で初めて作成します。続いて`AuthGate`が現在のセッションをアプリへ入れてよいか判断し、`AuthenticatedApp`をログイン後の製品画面とします。

## 日次レート順位

既存の「その他」から開く認証済みアカウント画面には、現在レート、前日順位、この端末でその画面を開いて実際に確認した最高の前日順位を表示します。取得のきっかけはアカウント画面を開くことだけです。アプリ起動、フォアグラウンド復帰、バックグラウンド処理では、この端末内の参照値を取得・更新しません。対局画面と研究画面はアカウント統計を担当しません。`refresh_rating_daily_snapshot(date)`は以前の行を1トランザクションで置き換えるため、データベースに残すのはクライアントが必要とする最新スナップショットだけです。内容は東京基準のスナップショット日、同順位を扱う`RANK()`順位、アクティブユーザー数、上位percentileです。すべてのアクティブユーザーについて、東京の締切時刻より前にある最新の`rating_history.rating`を使います。このため締切後に`ratings.current_rating`が変わっても前日順位は変わりません。

この機能で「順位集計のアクティブユーザー」とは、削除されておらず、既存の確定レート更新経路が`[cutoff - 30 days, cutoff)`に作成した`rating_history` 行を1件以上持つユーザーです。既存レート経路に仮レート用の別条件はないため、新しい最低対局数や仮レート除外は追加しません。この定義はアカウントライフサイクルの`profiles.last_active_at`とは意図的に分けています。Androidが所有者限定行を前日順位として受け入れるのは、`snapshot_date`が現在のAsia/Tokyo日付から1日引いた値と一致するときだけです。古い行と当日行は表示せず、端末内の最高値も更新しません。最高percentile/dateはSupabase Auth ユーザーUUID単位で保存しますが、サーバー公式実績ではなく、アカウント画面を開かなかった日を含まず、端末間で同期しません。

更新 関数は、空の`search_path`を持つ`SECURITY DEFINER`です。呼出し境界にはPostgreSQL関数 ACLを使い、`PUBLIC`、`anon`、`authenticated`にはexecute権限を与えず、`service_role`には与えます。この設計により、PostgREST JWT 取得が存在しない、明示的に権限を与えたデータベース 所有者のpg_cron ジョブも、状況依存の二重認可として`auth.role()`へ依存せず実行できます。このマイグレーション自体は本番Cronを導入しません。

この境界の正式なマイグレーションは`202608220029_daily_rating_snapshot.sql`です。マイグレーション番号028は、本番状態の監査後に未出荷候補を廃止したため、意図的な永久欠番です。1日1回のデータベース内呼出しにはCloudflareやGitHub ActionsではなくSupabase Cron/pg_cronを使います。外部ネットワーク hopや追加の本番データベース認証境界を作らず、スキーマを明示した関数を実行し、ジョブ/実行の確認場所をデータベースの近くに保つためです。マイグレーションはextension有効化やジョブ作成を意図的に行いません。これらは別の本番作業として実行・監査しました。詳細は[日次レートスナップショット運用](../04_レーティング/日次レートスナップショット運用.md)を参照してください。

確定済みで冪等なレート確定経路は、差分が0の場合も各playerへ`rating_history` 行を1件書きます。プロトコル 2はサーバー replayと確認材料（確認材料）の検査後、`release_finalize_result_v2`内でこれを行います。`(user_id, match_id)` 一意 インデックスと終了状態の再試行経路が、レート対象対局履歴の重複を防ぎます。異議あり・未完了結果は履歴を書きません。既存の整理処理はユーザーごとの最新100 行を残します。古い行が押し出されるユーザーは必ずより新しいレート対象対局を持つため、30日有効な条件には十分であり、より広い順位履歴の保持は追加しません。締切レートの再構築では、1人のユーザーが締切後に100局を終えるより前に日次更新が動くことを前提とします。現規模で現実的でないこの場合の保持変更は、この機能の対象外です。

## ゲーム中核（Game Core）

`Board`はcompactで変更不能な`IntArray` value objectであり、安全なoperationだけを公開します。`GameState.apply(Move)`は純粋な状態遷移です。非合法手を拒否し、すべての挟んだlineを反転し、手番を進め、1回のpassを処理し、連続passまたは盤面が埋まったときに終了します。`PositionHash`は決定的で、P2P 契約に使います。

## クライアント セッション状態とサーバー永続対局状態

Android 状態 machine（`IDLE`、`WAITING`、`SIGNALING`、`P2P_CONNECTED`、`PLAYING`、`MOVE_CONFIRMING`、`SYNCHRONIZING`、`RECONNECTING`、`FINISHING`、終了状態）は、1台の端末のセッションを表します。SupabaseはP2P channelを常時観測できないため、これらの状態を複製しません。プロトコル 2では、`matches.release_status`（`MATCHED`、`ACTIVE`、`RECONNECTING`、`RESULT_PENDING`、`CONFIRMED`、`DISPUTED`、`FORFEIT`、`EXPIRED`、`ABANDONED`）を永続ライフサイクルの正式状態とします。古い`matches.server_status`と`matches.status` 列は互換性境界として残しますが、プロトコル 2 ライフサイクルの正式状態ではありません。

## クライアント対局状態 machine

```text
IDLE -> WAITING -> SIGNALING -> P2P_CONNECTED -> PLAYING -> FINISHING -> CONFIRMED
                         |             |              |              |
                  SIGNALING_FAILED  DISCONNECTED  DISCONNECTED  PENDING_RESULT/DISPUTED
```

状態 machineは純粋なreducerです。UIは状態を観測するだけで、散在する条件分岐から遷移を決めません。

## P2Pの流れ

設計理由と現在の初回接続sequenceは[通常接続設計](../02_オンライン対局/通常接続設計.md)に記載します。再接続固有の障害処理は[再接続設計](../02_オンライン対局/再接続設計.md)に分けています。

1. キューへ後から参加したユーザーが対局を成立させます。データベースは参加者単位の`match_notifications` 行を保存し、待機中のAndroidクライアントは自分だけの行をRealtimeで観測して、すぐに`claim_active_match_v2()`を呼びます。通知の遅延やRPC応答喪失に備え、stable リクエストを使う定期確認／取得経路を代替経路として残します。
2. サーバーがBLACKへ割り当てた参加者がnon-trickle WebRTC OFFERを作り、参加者・epoch限定の`match_signals_v2` 行を`publish_match_signal_v2`で送ります。WHITEは同じ境界からANSWERを返します。
3. DataChannelは各端末で独立に開きます。各参加者がepochを指定した開始 ACKを1件書き、サーバーが双方のACKを報告した後でだけクライアントは`PLAYING`へ入ります。対局通知の購読は割り当て後に終えますが、signaling購読は再接続signalを観測できるよう`WebRtcMatchCoordinator`の生存期間に限定して維持します。
4. 各着手はDataChannelだけで送ります。すべての着手コマンドは`matchId`、`ply`、`move`、`commandId`、`previousStateHash`を含みます。投了、時間切れ、切断には別の終了用DataChannel control メッセージを使い、双方が同じ結果を提出できるようにします。このメッセージは着手を運べません。
5. 受信側はサーバーが割り当てた相手のdisc、コマンド fingerprint、冪等性、ply、合法性、hashを検証します。再利用したコマンド IDのペイロードが異なる場合はプロトコル エラーです。
6. 次のplayerに合法手がなければ、双方が端末内で強制passを適用し、同じ正規token `--`を追加します。通常UIにpass buttonは表示しません。

## 結果確定とレート

プロトコル 2の参加者は、正規化済み着手履歴、終了理由、必要な場合の敗者disc、sizeを制限した最終時計 確認材料を`submit_match_result_v2`で提出します。Android アダプターはクライアントが正式とみなすwinnerや最終 hashを送りません。サーバーは正常終了の確認材料を決定的に再生して結果と最終 hashを導出し、両参加者が同じ正規化済み履歴を提出したことを確認してから、1つの冪等トランザクションで記録を作成し、バージョン付き`RatingPolicy`を適用します。不一致は`DISPUTED`となり、レートを変更しません。正常終了の提出が片側だけなら`RESULT_PENDING`です。

新しいGameRecordは、検証済みの最終局面hashと製品固定の`5m`持ち時間を保存します。マイグレーション 017より前の既存記録は最終 hashがnullの場合がありますが、記録は変更不能のままです。

`RatingPolicy`と`StableRatingPolicy`は交換可能なインターフェースです。最高値は単調増加です。安定帯は最近の完了レートを使い、十分な観測数が揃うまで`CALCULATING`を返します。

## レビュー / Edax

`ReviewSession`はcursorとvariationを所有し、`GameRecord`を変更しません。`AnalysisEngine`は`analysis:api`の背後に置き、レビュー機能から全合法手の評価を依頼します。`EvaluationScore`は手番側から見た値と`EXACT` / `HEURISTIC` / `BOOK`の種別を持ちます。`analysis:edax`はJNI、Edax固有変換、cancel、識別情報を含む32局面memory キャッシュ、SAFから非公開ストレージへのデータ管理を担当します。評価値とレビューのvariationを`GameRecord`へ永続化しません。

Edax評価データとopening bookはユーザーがimportするもので、アプリアセットにはしません。キャッシュキーは正規盤面、手番、Edax レベル、eval SHA-256、任意のbook SHA-256を含みます。このためデータを置き換えた後に古い評価値を再利用できません。有効なbook 1つを名前付きスロット境界として表現し、将来複数bookを切り替えても`analysis:api`を変更しない構成です。

## アカウント削除

Androidが作成できるのは所有者限定の削除リクエストだけです。信頼済みワーカーはサービスロール（service_role）だけが呼べるDB準備RPCを実行し、Research 対象者とアカウントの対応を解除し、Auth 管理者 APIでAuthの識別情報を削除してからリクエストを完了扱いにします。DB準備では非公開 レートと記録参照を削除しますが、相手側の変更不能な共有記録と対局 外部 キーを有効に保つため、内部識別情報 tombstoneを残します。削除リクエストが保留中のアカウントはmatchmakingから除外します。

## セキュリティ境界と禁止する依存

- 対局中の着手や時計をSupabaseへ書きません。
- Realtime Postgres Changesを使うのは、参加者限定の対局成立通知（`match_notifications`）とSDP signaling（プロトコル 2では`match_signals_v2`）だけです。対局通知の観測は割り当て後に終えます。signalingは再接続調整も運ぶため、`WebRtcMatchCoordinator` セッションの範囲で観測します。着手、時計、盤面状態、結果、レートにはRealtimeを使いません。
- サービスロール（service_role） キーをAndroidやbrowserへ配布しません。
- Androidからレート、最高レート、公式結果を直接更新できません。
- 対局はEdaxを参照できず、レビューだけが`AnalysisEngine`を参照できます。
- 実行中のmatchmaking、時計、着手transport、結果提出、レートは`AnalysisEngine`を作成・呼出ししません。
- GameRecordは確定後に変更できません。
- SQLはRLSを有効にし、クライアントによる状態更新の代わりに用途を絞ったRPCを公開します。
- Matchmakingは公式`ratings.current_rating`のスナップショットを使い、TTL付きキュー 行と`FOR UPDATE SKIP LOCKED`を使用します。クライアントが指定したレートは受け入れません。
- `active_match_participants.user_id`は、1ユーザーにつき進行中の対局を1つにするデータベース不変条件です。プロトコル 2の`MATCHED` 行は2分の初回leaseを持ち、abandon処理と件数を制限したmaintenance経路がレートを変えずに予約を解放します。
- `submit_match_result_v2`は冪等な確認材料を保存し、サーバー replayと確認材料規則を満たした後でだけ確定します。ペイロード enum、時計 size、正規token形式、合法replay、終了状態、サーバーが導出した結果／hashをSQLで検査します。
- 終了済み対局、記録、submissionには保持・クリーンアップ RPCがあります。内部pruning／クリーンアップ 関数のexecute権限を`anon`、`authenticated`、`PUBLIC`へ与えず、`SECURITY DEFINER` 関数は空の`search_path`を使います。
- DataChannelの着手コマンドが運ぶのは実着手だけです。終了用control メッセージは別のwire typeです。`TurnResolver`は双方の端末で決定的に`--`を追加し、コマンド IDはペイロードが拒否された場合も最初のペイロードを予約します。
