| 関連ワークフロー / ワーカー | Supabase Cron ジョブ `daily-rating-snapshot`（ジョブID `1`）、コマンド `select public.refresh_rating_daily_snapshot();`。Cloudflare / GitHub Actionsでは動かさない |
| 関連ドキュメント | [日次レートスナップショット運用](../04_レーティング/日次レートスナップショット運用.md)、[本番移行記録 029](../09_履歴/本番移行記録_202608230029.md)、[システム構成](システム構成.md) |
| 本番状態 | 029適用済み。`pg_cron` 1.6.4を`pg_catalog`へ導入し、有効なジョブ 1件を登録済み。2026-08-22分の初回スナップショットは5行。初回定期実行は2026-08-24 00:10 JST |
| 注意事項 | 028を復活・適用しない。029、extension、ジョブは別々の本番操作として監査済み。Cron失敗時もAndroidは古いスナップショットを前日順位に使わない |

029の完成仕様は次のとおりです。

- 締切はAsia/Tokyoのスナップショット日の翌日00:00。`rating_history`から締切より前の最新レートを復元します。
- アクティブユーザーは未削除で、`[cutoff - 30 days, cutoff)`に確定レート更新が1件以上あるユーザーです。`profiles.last_active_at`は使いません。
- レート降順、同率は`RANK()`、`top_percentile = rank / active_user_count * 100`です。
- データベースは最新 スナップショットだけを保持します。同一スナップショット日の再試行は既存結果を変えず、古いdateへの巻き戻しを拒否します。
- Androidはスナップショット日がAsia/Tokyo基準の本当の前日と一致する場合だけ「前日順位」として表示します。古い・当日・取得失敗の行は表示にも端末内 最高更新にも使いません。
- 「この端末で確認した最高の前日順位」は、ユーザーがAccountScreenを開いて有効な前日順位を確認できた時だけUUID単位で更新する参考値です。サーバー実績・履歴・端末間同期ではありません。

## 9. GitHub Actions全体

`.github/workflows/`に存在するワークフローは次の2件です。GitHub Actions内にデプロイ ワークフローはありません。LP本番デプロイはGitHub ActionsではなくCloudflare Workers Buildsのリポジトリ連携です。

| ワークフロー | 分類 | トリガー / スケジュール | Runner / タイムアウト | 認証情報 | 主な処理 | 状態・確認場所 |
|---|---|---|---|---|---|---|
| `CI` (`ci.yml`) | CI / ビルド / テスト | `push`, `pull_request` | `ubuntu-latest` / ジョブ タイムアウト明示なし | 自動`GITHUB_TOKEN`（checkout用途）。本番 認証情報なし | 管理ワーカー typecheck/テスト、Android テスト/lint/debug・リリース・AAB、境界・SQL セキュリティ・リリース内容、端末内 Supabase pgTAP | 稼働中。GitHub Actions 実行 / step ログ。デプロイなし |
| `Research batch` (`research-batch.yml`) | 本番定期処理 / 手動運用 | `17,47 * * * *`、`workflow_dispatch` | `ubuntu-latest` / 30分 | GitHub Environment `research-production`の`RESEARCH_BATCH_DATABASE_URL` | 上限付き 検証器（最大200）と集計（最大500） | 稼働設定あり。concurrency `research-production-batch`、cancelなし。GitHub Actions 実行 / step ログ |

| 処理 | 実行基盤 | スケジュール | 目的 | 状態 | 監視場所 |
|---|---|---|---|---|---|

### Supabase内の定期処理

本番には`pg_cron` 1.6.4が`pg_catalog`へ導入され、`cron.job`には前日順位用の有効なジョブ `daily-rating-snapshot`（ジョブID `1`）だけが存在します。登録コマンドは`select public.refresh_rating_daily_snapshot();`だけです。READMEに候補として記載された対局ライフサイクル クリーンアップ関数群を呼ぶSupabase Cron ジョブはありません。実行履歴はジョブ詳細のCron ログまたは`cron.job_run_details`で確認します。

## 11. シークレット / 認証情報境界

シークレットの実値はリポジトリ、issue、運用ログ、この文書へ記録しません。

| シークレット / 認証情報 | 利用主体・用途 | 保管場所 | クライアントへ渡してよいか |
|---|---|---|---|
| Android Supabase publishable / anon キー | AndroidからAuth / RLS / RPC / Realtimeへ接続 | 開発はuntracked `local.properties`または環境変数、ビルド時にBuildConfig | **可**。公開クライアント キーとしてRLS前提。サービスロール（service_role）と混同しない |
| ユーザー Auth セッション JWT / 更新 token | 本人としてSupabaseへアクセス | Supabase Android SDKの端末内セッション、Web 復旧では一時リンク context | 本人クライアントだけ。ログ・文書・別ユーザーへ渡さない |
| `SUPABASE_ANON_KEY` | 公開ワーカーからSupabase Auth / RESTへアクセス | Cloudflare ワーカー `chanriva` シークレット | 公開 キー相当だが現在の保管境界はワーカー。サービスロール（service_role）へ置換しない |
| `SUPABASE_SERVICE_ROLE_KEY` | `othello-admin`が信頼済み削除RPCとAuth 管理者 APIを実行 | Cloudflare ワーカー `othello-admin` シークレット | **不可**。Android、browser、公開ワーカー、GitHub バッチへ渡さない |
| `ADMIN_TOKEN` | `othello-admin`の手動管理endpointをBearer認証 | Cloudflare ワーカー `othello-admin` シークレット | **不可**。operatorだけが必要時に使用し、ログへ出さない |
| `RESEARCH_BATCH_DATABASE_URL` | DB ロール `research_batch`でwrapper 関数だけを実行 | GitHub Environment `research-production` シークレット | **不可**。Android / Cloudflareへ渡さない |
| Supabase DB 所有者 認証情報 | マイグレーション、DB 所有者限定操作、Cron管理 | Supabase / operatorの認証情報 store。リポジトリや通常ワークフローへ保存しない | **不可** |
| Cloudflare Workers Builds連携認証情報 | GitHub mainからワーカーをビルド / デプロイ | Cloudflare / GitHubの連携設定 | **不可**。アプリやリポジトリへ埋め込まない |
| 自動`GITHUB_TOKEN` | ワークフロー checkout等 | GitHub Actionsが実行単位で発行 | クライアントへ渡さない。ワークフロー permissionsを最小化する |

`SUPABASE_URL`、`ANDROID_MIN_VERSION_CODE`、`NODE_EXTRA_CA_CERTS`で指定するリポジトリ内CA certificate パスはシークレットではありません。シークレットでない値も、権限境界を広げる代替認証情報として扱わないでください。
