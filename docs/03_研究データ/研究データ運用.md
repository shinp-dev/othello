## ワーカー設定

信頼済みCloudflareワーカーは`othello-admin`です。アカウント削除と運用者向けHTTPリクエストを処理しますが、Researchの検証や集計は実行しません。秘密ではない変数は`cloudflare-admin/wrangler.toml`にあります。次の値はワーカーのシークレットストアだけに設定します。

- `SUPABASE_SERVICE_ROLE_KEY`
- `ADMIN_TOKEN`

サービスロール（service_role）キーを使うのは、ワーカーがサービス限定RPCを呼ぶ場合だけです。`ADMIN_TOKEN`は運用者向けHTTPエンドポイントを保護します。どちらの値もコミットしないでください。

## Research バッチ実行基盤

Researchの検証と集計は[`.github/workflows/research-batch.yml`](../../.github/workflows/research-batch.yml)で毎時17分・47分に実行し、`workflow_dispatch`でも手動実行できます。ワークフローは`shinp-dev/othello`の`main`だけで動き、GitHubトークンの権限は読み取り専用、タイムアウトは30分、同時実行グループは1つです。

マイグレーション022は、ログイン不能で権限を継承しないロール`research_batch`を作成します。マイグレーションの検証後、Gitの外で強いランダムパスワードを生成し、信頼済みSupabase SQL操作面でこのロールのログインを有効にします。トランザクションプーラーの接続URLだけを、GitHub Environment `research-production`のシークレット`RESEARCH_BATCH_DATABASE_URL`へ保存します。ワークフローへSupabase `service_role`、プロジェクトのデータベース所有者パスワード、JWT署名シークレット、Cloudflare認証情報を渡してはいけません。

このロールはテーブルやシーケンスへ直接アクセスできず、件数を制限したResearchのclaim / complete / append / checkpoint / publish / fail用ラッパー関数だけを実行できます。GitHub-hosted runnerはIPv4だけを使うため、URLにはSupabaseの共有トランザクションプーラーを指定し、`sslmode=verify-full`を要求します。ワークフローはプロジェクトDashboardのSSL設定から取得したSupabase公開証明書`prod-ca-2021.crt`をNodeの信頼ストアへ追加します。接続失敗を回避するために証明書やホスト名の検証を無効にしてはいけません。GitHub Environmentは`main`ブランチに制限します。ロールのパスワードをローテーションするときは、PostgresとEnvironmentのシークレットを同時に更新します。

Hosted環境の契約テストは、`LOGIN`を有効にする前後の両方でロール権限を検証します。導入状態を確認するときは`rolcanlogin`を別に調べます。

1回の実行で最大200対局を検証し、変更不能な1世代へ最大500対局を追加します。検証リースは5分で期限切れになります。集計処理は世代を失敗扱いにせず、リースを期限切れにしてチェックポイントを残します。次の実行がその処理を回収し、`generation_processed_games`にない対局だけを選びます。このため実行環境が終了しても、作業は失われずPostgresに未処理分として残ります。決定的に不正な受理済み元データは、新しい世代だけを`FAILED`にし、以前の公開済み世代は有効なままにします。

既定の1時間2回のスケジュールでは、集計の未処理分を消化する目安は100対局で1回、1,000対局で2回、10,000対局で約20回、100,000対局で約200回です。これは処理能力の見積りであり、処理時間の保証ではありません。GitHubのスケジュール実行は遅延・欠落することがあります。その場合はワークフローを手動実行して復旧します。公開リポジトリは課金対象時間を消費せず標準のホステッドランナーを利用できますが、リポジトリに60日間活動がない場合は定期実行ワークフローが無効になるため、再度有効にする必要があります。

検証は1回につき別枠で200対局に制限します。100対局は1回、1,000対局は約5回、10,000対局は約50回、100,000対局は約500回です。1時間に2回成功する場合は約10.5日かかります。新しい行は後続実行まで`PENDING`のままです。上限やスケジュール頻度の引上げは明示的な運用変更であり、正しさを保つための必須条件ではありません。

GitHub Actionsを選んだ理由は、Workers Freeが現在1回の呼出しあたり10 ms CPUと50件の外部サブリクエストに制限されているためです。Reversiの独立した棋譜再生と世代全体のループは対局数に応じて増えるため、長期的に安全なCron処理ではありません。Cloudflareアカウントは軽量なオンライン・管理用途に残します。

## 収集の有効化と緊急停止

収集前のスモークテスト確認が成功するまで、有効なポリシーを無効に保ちます。

```sql
select collection_enabled
from research_private.policy_versions
where is_active;
```

緊急停止:

```sql
update research_private.policy_versions
   set collection_enabled = false
 where is_active;
```

この操作は、新しい収集とプライバシー保護APIの応答を停止します。受理済みResearchデータを削除せず、オンライン対局、レート、GameRecord、Edaxも停止しません。

すべての有効化確認が成功した後、有効なポリシー行だけを変更します。

```sql
update research_private.policy_versions
   set collection_enabled = true
 where is_active;
```

100人／20人のしきい値用テストデータを本番で作ってはいけません。

## 監視

次の問い合わせは信頼済みSQL操作面からだけ実行します。

```sql
select validation_status, count(*)
  from research_private.games
 group by validation_status
 order by validation_status;

select generation_id, status, created_at, published_at, failure_code
  from research_private.aggregation_generations
 order by generation_id desc
 limit 5;

select pg.generation_id, g.status, g.published_at
  from research_private.published_generation pg
  join research_private.aggregation_generations g using (generation_id)
 where pg.singleton;
```

検証の未処理件数と拒否率、最後に成功した公開済み世代、`BUILDING` / `FAILED`世代、定期実行ワークフローの失敗または経過時間、RPCエラー、現在の収集フラグを監視します。研究対象者IDや生の着手データを公開ログやサポートメッセージへ複製しないでください。Researchバッチワークフローの成功が予定2回分を超えて存在しない場合は、運用アラートを上げます。

## 失敗した世代の復旧

1. 新しい収集へ影響する可能性があれば、`collection_enabled=false`にします。
2. 最新の`FAILED`世代と非公開の`failure_code`を調べます。
3. 非公開Researchテーブルから原因となった受理済みデータを特定します。
4. 受理済み元データを自動削除しないでください。
5. レビュー済み変更でデータまたはコードを修正し、Researchバッチワークフローを手動実行します。新しい世代が`PUBLISHED`になり、参照先が1トランザクションで切り替わるまで、以前の公開済み世代は有効なままです。
6. 非公開ACLと公開応答の検査を再実行します。

リース期限切れとActionsの再試行は、想定済みの復旧経路です。処理不能なデータが、他の保守処理を永久に止めてはいけません。

## アカウント削除の確認

削除リクエストは開いているResearch参加期間を閉じ、対象者を`DELETION_PENDING`にします。ワーカーは`prepare_account_deletion`の後、Auth削除の前にサービス限定の切り離しRPCを呼びます。このRPCは冪等です。切り離し後は`account_user_id`が`null`、`link_state=UNLINKED`になり、受理済み提供者と集計の重みは残ります。

## ロールバックと障害対応

- 研究テーブルや受理済み提供者を削除してロールバックしないでください。
- 最初にサーバー側で収集を無効にします。
- 調査中も最後の公開済み世代を維持します。
- 以前のバージョンがアカウント切り離しの順序を守る場合に限り、ワーカーをロールバックします。実行環境に問題がある場合は、定期実行するResearchワークフローを別に無効化します。
- マイグレーションのロールバックは自動では行いません。レビュー済みの追加マイグレーションを使います。
- シークレットや個人に結び付く生データを記録せず、UTC時刻、プロジェクト参照、ワーカーのデプロイバージョン、影響を受けた世代、復旧結果を記録します。
