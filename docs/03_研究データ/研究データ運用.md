## Research バッチ実行基盤

Research 検証と集計は[`.github/workflows/research-batch.yml`](../../.github/workflows/research-batch.yml)で毎時17分・47分に実行し、`workflow_dispatch`でも開始できます。ワークフローは`shinp-dev/othello`の`main`だけで動き、GitHub tokenは読み取り専用 permission、タイムアウトは30分、concurrency groupは1つです。

マイグレーション 022は、login不能で権限継承しないロール `research_batch`を作成します。マイグレーションの検証後、Gitの外で強いrandom パスワードを生成し、信頼済みSupabase SQL操作面でこのロールのloginを有効にします。トランザクション poolerの接続URLだけを、GitHub Environment `research-production`のシークレット `RESEARCH_BATCH_DATABASE_URL`へ保存します。ワークフローへSupabase `service_role`、プロジェクト データベース 所有者 パスワード、JWT 署名 シークレット、Cloudflare 認証情報を渡してはいけません。

このロールはテーブルやsequenceへ直接アクセスできず、件数を制限したresearch 取得 / complete / append / チェックポイント / publish / fail wrapperだけを実行できます。GitHub-hosted runnerはIPv4だけを使うため、URLにはSupabase shared トランザクション poolerを指定し、`sslmode=verify-full`を要求します。ワークフローはプロジェクト DashboardのSSL設定から取得したSupabase公開certificate `prod-ca-2021.crt`をNodeのtrust storeへ追加します。接続失敗を回避するためにcertificateやhostnameの検証を無効にしてはいけません。GitHub environmentは`main` ブランチに制限します。ロール パスワードをrotateするときは、Postgresとenvironment シークレットを同時に更新します。

hosted 契約は、LOGINを有効にする前後の両方でロール権限を検証します。導入状態を確認するときは`rolcanlogin`を別に調べます。

1回の実行で、最大200 対局を検証し、変更不能な1 世代へ最大500 対局を追加します。検証 leaseは5分で期限切れになります。集計 実行は世代を失敗扱いにせず、leaseを期限切れにしてチェックポイントします。次の実行がその処理を回収し、`generation_processed_games`にない対局だけを選びます。このためrunnerが終了しても、作業は失われずPostgresにbacklogとして残ります。決定的に不正な受理済み元データは、新しい世代だけを`FAILED`にし、以前の公開済み世代は有効なのままにします。

既定の1時間2回のスケジュールでは、集計 backlogを処理する目安は100 対局で1 実行、1,000 対局で2 実行、10,000 対局で約20 実行、100,000 対局で約200 実行です。これはbacklog throughputの見積りであり、latency保証ではありません。GitHubのスケジュール実行は遅延・欠落することがあります。復旧経路はmanual 分配です。公開 リポジトリは課金対象minuteを消費せず標準hosted-runner timeを利用できますが、リポジトリ activityが60日ない場合は定期実行ワークフローが無効になるため、再度有効にする必要があります。

検証は1 実行につき別枠で200 対局に制限します。100 対局は1 実行、1,000 対局は約5 実行、10,000 対局は約50 実行、100,000 対局は約500 実行です。1時間に2回成功する場合は約10.5日かかります。新しい行は後続実行まで`PENDING`のままです。上限やスケジュール頻度の引上げは明示的な運用変更であり、正しさを保つための必須条件ではありません。

GitHub Actionsを選んだ理由は、Workers Freeが現在1 invocationあたり10 ms CPUと50 external subrequestに制限されているためです。Reversiの独立replayと世代全体のloopは対局数に応じて増えるため、長期的に安全なCron workloadではありません。Cloudflare アカウントは軽量なオンライン / 管理者用途に残します。

## 収集の有効化と緊急停止

収集前のスモークテスト確認が成功するまで、有効なポリシーを無効に保ちます。

```sql
select collection_enabled
from research_private.policy_versions
where is_active;
```

緊急停止:

```sql
update research_private.policy_versions
   set collection_enabled = false
 where is_active;
```

この操作は、新しい収集とprivacy API 応答を停止します。受理済みresearch データを削除せず、オンライン 対局、レート、GameRecord、Edaxも停止しません。

すべての有効化確認が成功した後、有効なポリシー行だけを変更します。

```sql
update research_private.policy_versions
   set collection_enabled = true
 where is_active;
```

100人／20人のしきい値用テストデータを本番で作ってはいけません。

## 監視

次の問い合わせは信頼済みSQL操作面からだけ実行します。

```sql
select validation_status, count(*)
  from research_private.games
 group by validation_status
 order by validation_status;

select generation_id, status, created_at, published_at, failure_code
  from research_private.aggregation_generations
 order by generation_id desc
 limit 5;

select pg.generation_id, g.status, g.published_at
  from research_private.published_generation pg
  join research_private.aggregation_generations g using (generation_id)
 where pg.singleton;
```

検証 backlog／reject率、最後に成功した公開済み世代、`BUILDING` / `FAILED` 世代、定期実行ワークフローの失敗または経過時間、RPC エラー、現在の収集flagを監視します。研究対象者IDや生の着手データを公開ログやサポートメッセージへ複製しないでください。Research バッチ ワークフローの成功が予定2回分を超えて存在しない場合は、運用alertを上げます。

## 失敗した世代の復旧

1. 新しい収集へ影響する可能性があれば、`collection_enabled=false`にします。
2. 最新の`FAILED` 世代と非公開な`failure_code`を調べます。
3. 非公開 研究テーブルから原因の受理済みソースを特定します。
4. 受理済み元データを自動削除しないでください。
5. レビュー済み変更でデータまたはコードを修正し、Research バッチ ワークフローをmanual 分配します。新しい世代が`PUBLISHED`になりpointerが1トランザクションで切り替わるまで、以前の公開済み世代は有効なのままです。
6. 非公開 ACLと公開応答の検査を再実行します。

lease期限切れとActionsの再試行は、想定済みの復旧経路です。処理不能なソースが、他のmaintenance taskを永久に止めてはいけません。

## アカウント削除の確認

削除リクエストは開いているresearch 期間を閉じ、対象者を`DELETION_PENDING`にします。ワーカーは`prepare_account_deletion`の後、Auth削除の前にservice限定切り離し RPCを呼びます。このRPCは冪等です。切り離し後は`account_user_id`がnull、`link_state=UNLINKED`になり、受理済み提供者と集計の重みは残ります。

## Rollback / incident手順

- 研究テーブルや受理済み提供者を削除してrollbackしないでください。
- 最初にサーバー側で収集を無効にします。
- 調査中も最後の公開済み世代を維持します。
- 以前のバージョンがアカウント 切り離しの順序を守る場合に限り、ワーカーをrollbackします。runnerに問題がある場合は定期実行 Research ワークフローを別に無効化します。
- マイグレーション rollbackは自動では行いません。レビュー済みの追加マイグレーションを使います。
- シークレットや生データ personal データを記録せず、UTC時刻、プロジェクト ref、ワーカー deployment バージョン、影響を受けた世代、復旧結果を記録します。
